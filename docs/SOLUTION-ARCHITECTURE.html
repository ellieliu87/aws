Terms used in this document
State machine
A workflow written down as data — a list of named steps and what comes after each one. AWS reads that definition and runs it, remembering where every execution has got to. Called a state machine because a running execution sits in exactly one step at a time and moves between them along defined transitions.
Step Functions
The AWS service that stores and runs state machines. It is what makes "wait for a person to approve this" survive a restart: the waiting belongs to the service, not to any running process.
Compile / deploy
Compiling turns the analyst's canvas into a state machine definition. It is pure computation — data in, data out, no AWS involved. Deploying is the call that turns that definition into a real, runnable thing in the AWS account. They need very different permissions, which is the point of §6.5.
Lambda
Runs a piece of code on demand without a server to maintain. You are billed per invocation, so idle costs nothing. Its constraint is a hard fifteen-minute ceiling per run.
Fargate
Runs a long-lived container without a server to maintain. Suited to something that must stay up and answer requests, where Lambda suits short bursts of work. This is where the web tier runs — two replicas of it — while the solver stays on Lambda for the opposite reason. §6.12 is about why the same account uses both.
Replica
One of several identical copies of the application running at the same time, so that one failing does not take the service down. Making more than one copy possible is what most of this document is about.
Queue / dead-letter queue
A queue holds work to be done later so the website does not have to wait for it. A dead-letter queue is where a message goes after it has failed several times — so failures are kept for inspection rather than silently discarded.
Token
The thing your browser sends with every request to prove who you are. The distinction that matters here: a token can be a reference the server must look up, or a signed document carrying the facts inside it. §6.3 is about moving from the first to the second.
Role
An identity a piece of software assumes to get permission to do something, instead of holding a stored username and password. "Passing a role" — attaching one to a resource you are creating — is a powerful permission, because whoever can pass roles can potentially attach one more privileged than they hold.
Cold start
The extra delay on the first request after a period of inactivity, while the environment is prepared. The price of paying nothing while idle.

1What the system does

The CMA Workbench is a self-service analytics platform for the analysts who produce a bank's capital-planning numbers — the deposit balance forecasts and net-interest-income projections that feed CCAR stress testing and the annual outlook.

Before a tool like this, that work is spreadsheets and one-off scripts. The workbench gives an analyst four things in one place:

  • Data — connect to a warehouse table or upload a file, and see its schema and sample rows immediately.
  • Models — register an existing model artifact, or train a regression in the browser against bound data.
  • Workflows — draw a pipeline on a canvas (data → transform → model → output), run it, and download the result.
  • Agents — ask questions in plain language, with AI agents that can read the datasets, models, and runs the analyst is looking at.

The characteristic that drives the architecture: the numbers this produces get filed with a regulator. That single fact shaped more of the design than any performance requirement did.

2Why it needed re-architecting

The original build kept everything it knew in the memory of one running process. Every dataset, every registered model, every completed run, every logged-in user's session.

Three consequences followed, and the third is the one that matters:

  1. Restarting lost work. Deploy a fix on Friday afternoon and every dataset an analyst uploaded that week was gone.
  2. It could not scale. A second server would not help. The two would disagree about reality: a dataset uploaded to one was invisible to the other.
  3. There was no durable record of what happened. If a regulator asked "which calculation produced this number?", the honest answer was that the evidence lived in a process that had since restarted.

The diagnosis matters more than the symptoms. This was not a deployment problem. No amount of load balancing, auto-scaling or containerisation fixes a process that holds its own truth. It was a data design problem, and it had to be fixed as one before any hosting change would mean anything.

That is the thesis of this document, and it explains the order everything happened in.

3Principles applied throughout

Five rules shaped every decision that follows.

Fix the data design before the hosting

Moving state out of the process is what makes a second server worth having. Do it the other way round and you get servers that disagree with each other, which is worse than one honest server.

Every AWS dependency is optional

Every integration checks for its configuration and falls back to local behaviour when it is missing, so a developer with no AWS account still runs the full application. This is not convenience for its own sake. It means the fallback path gets exercised every day, so it still works on the day it is needed.

Prefer managed services with no idle cost

A handful of analysts use this system, in bursts. Anything that bills for standing capacity is the wrong shape here, whatever its technical merits.

Make the audit trail a property of the design, not a feature

Versioned artifacts, retained execution history, and immutable compiled plans are cheaper to build in from the start than to add under regulatory pressure.

Say plainly what is built, and separately what is proved

This started as one rule and had to become two. Everything in §8 is built and deployed, and several rows are still qualified. "Deployed" and "a real user has done it" are different claims, and the gap between them is where a document like this usually starts to lie.

4How the platform works

Two distinct paths through the system, with different requirements.

The interactive path

An analyst clicks something and the answer comes straight back: browsing datasets, previewing data, editing a chart, talking to an agent. These are short, chatty and latency-sensitive. Agent replies stream back word by word over a connection held open for the duration, which is why the web tier has to be a long-lived process.

The workflow engine

An analyst draws a pipeline on a canvas and runs it. This is the heart of the product, and it works like this:

  1. Validate before running. The canvas is checked while the diagram is still on screen: circular dependencies, a model with no input, a model expecting a column the upstream data does not have. Fixing a broken pipeline before it runs is far cheaper than after.
  2. Work out the order. The pipeline is a dependency graph, so the engine sorts it into an execution order and rejects anything circular.
  3. Resolve the inputs. Each step's input is assembled from whatever feeds it: a scenario, an uploaded dataset, a warehouse table, or an earlier model's output.
  4. Run each model in isolation. Model artifacts are third-party code. They execute in a separate sandboxed process with a time limit, so a model that hangs or crashes cannot take the platform down with it.
  5. Record every run. Inputs, outputs, timing, status, and the scenario context are all retained.
  6. Write the outputs. Results go to a CSV download or a warehouse table. Where several models feed one output, such as three deposit models feeding a net-interest-income calculator, their results are merged and labelled by source.
  7. Explain failures in the analyst's language. Failures come back as named causes with a plain-English hint (FEATURE_MISMATCH, DQC_FAILED, TIMEOUT), not a stack trace. An analyst who can read the error can usually fix it themselves.

Analysts can save named pipelines and reload them. The in-progress canvas also survives a browser reload independently, so switching tabs never loses work.

How the records are organised

What code runs where

The services above say what is running. This says which code is running on each of them — a different question, and the one that decides how the repository is packaged.

Application code is not stored the way records are. It is built into an image, the image is kept in the container registry, and a compute service runs it. So "where does this folder live in the cloud" has two answers that are easy to conflate: the registry is where it lives, and the compute service is where it runs.

Two images, not one. The obvious approach ships one image everywhere, and it would work — the worker would just ignore the code it never calls. What it would cost is size. The worker image carries the numerical stack because it unpickles real model artifacts, and that alone is most of the registry's free allowance. Folding in the web framework, the agent runtime and the domain packs would make every cold start pull an image several times larger for the sake of one file. Two images means each one contains what it actually runs.

One thing is in neither image: the models themselves. An uploaded artifact is never deployed as code. It is data in object storage, named in the payload and fetched by the worker when it runs. That is why adding a model needs no deploy, and why every workflow step invokes the same single function instead of one function per model.

Nor is anything an analyst creates. Uploaded skills and the built search index used to sit on the disk of whichever server received them, and that is the one thing that would have made a second replica genuinely dangerous. Not a crash — two servers answering the same question differently, with nothing reporting a problem. Both now live in object storage, and each server keeps a local copy that it reconciles at startup, and for skills on a short interval afterwards. A skill is found by listing a folder rather than by name, so a missing one raises nothing. This was the last thing tying a request to a particular machine.

The same service, two opposite answers. §6.12 argues the solver should stay on functions rather than containers, and that is still true: solves are short, bursty, and scale to zero. The web tier reaches the opposite conclusion about the same service, because it is a long-lived process serving requests. Both answers are in this document, and reading one as the answer to the other is the easiest mistake to make here.

6Design decisions and trade-offs

Each one gives the problem, the options, what was chosen, how it was built, and what it cost.

Three of these needed no AWS service at all. 6.6 is a language feature, 6.9 is twenty lines of application logic, and 6.5 uses less AWS than the obvious implementation. Reaching for a service is a choice like any other, and the How row says so when the answer was not to.

6.1 — Externalising state before changing the hosting

Problem
The application could not run as more than one copy.
Options
Add sticky sessions at the load balancer so each user always returns to the same server; or move the state out of the process.
Chose
Move the state out. Sticky sessions hide the problem instead of solving it: a restart still loses that user's work, and an overloaded server still cannot hand anything to another.
How

Amazon DynamoDB, reached through one module that exposes four operations — get, put, delete, list — over plain dictionaries. Each registry gained matching accessors in place of its dictionary.

One seam, not database calls scattered through the code. It is the only place that knows storage exists, which is why the cache in 6.6 and the index in 6.7 could be added without touching a single caller. With no table configured it falls back to an in-process dictionary, so the original behaviour is still a code path that runs every day.

Gave up
Reads that used to be instant memory lookups became network calls. That cost was real and had to be paid back — see 6.6.

6.2 — One table, not one per record type

Problem
Four kinds of record needed durable storage.
Chose
A single table, where each record's key is its type plus its id. Fewer things to provision, monitor and back up. Four tables would buy separation the application never uses, because nothing queries across types.
How

One DynamoDB table declared in AWS CDK, so the infrastructure is version-controlled alongside the application. Records are grouped by type and identified by id within it — see the diagram in §5. On-demand billing, so an idle system bills nothing.

Gave up
It is less immediately obvious to someone browsing the console. A diagram and this document are the mitigation.

6.3 — Stateless tokens instead of a shared session store

Problem

Sessions lived in one server's memory, so a second server rejected tokens the first one issued.

An earlier version of this document called this "the last thing preventing horizontal scaling". That was wrong. Six other registries still held analyst-created work in memory: charts, Python tools, dashboard layouts, playbooks, analytic definitions, warehouse connections. Auth was just the one that would have broken every request instead of one feature.

The lesson is about how to audit this kind of problem. "Where does state live?" has to be answered by searching, not by remembering. One search for module-level dictionaries found all six in about a minute, after I had twice claimed there were none.

Options
Move sessions to a shared store (a database or a cache), or stop needing a session lookup at all.
Chose

The second. A Cognito token is signed and carries the user's identity, role, department and group memberships inside it. Any server can check it against Cognito's public keys. No lookup, so nothing to share.

A shared session store is still a shared dependency — another thing to scale, another thing whose outage takes you down. Checking a signature needs only the token and a cached public key.

How

Amazon Cognito holds the users and issues the tokens. The application verifies them itself: it fetches the pool's public keys once, caches them, and checks each token's signature, expiry, issuer, audience and type on every request.

Job title and department ride along as custom attributes; group membership arrives as a standard claim and feeds the existing permission filter unchanged. Sixty seconds of clock tolerance, because a token issued a moment ago can look slightly future-dated to a machine whose clock differs. That one was found the hard way, against the real pool.

Gave up

A signed token cannot be un-signed. Signing someone out stops them getting new tokens, but the one already in their browser works until it expires. Hence the one-hour lifetime: the expiry window is the revocation window.

A revocation denylist would close that gap, and would put back the exact shared lookup this design removed. If instant revocation were a requirement, which is plausible for a privileged-access system, the denylist would be the right answer and that cost would be worth paying on purpose.

Then
This decision settled how a token is verified. It left untouched the question of how one is obtained — which turned out to be the more interesting half, and is §6.13.

6.4 — Human approval as a durable state, not application code

Problem
Model governance requires a person to review results before they are published. Written in application code, the process has to stay alive while it waits, which could be hours or days. A restart mid-wait strands the run, so you also need a repair routine to find and clean up the wreckage.
Chose

Move the sequence into a state machine: a workflow written down as data, which AWS runs for you and which remembers where each execution has got to. "Wait for a human" becomes one of the steps, so the execution parks there until the reviewer answers. Restarts and deployments do not disturb it.

The approval gate is a control, and controls have to be evidenced. One built as a convention that a repair routine tidies up after is hard to show an examiner. One built as a state machine has an execution history showing who approved what, and when.

How

AWS Step Functions, using its wait-for-callback pattern. At the gate the execution hands out a one-time token and stops, consuming nothing while it waits. The approval endpoint returns that token and the execution picks up exactly where it paused.

A twenty-four hour limit on the wait, with the expiry wired to its own explicit end state rather than left to time out silently.

Gave up
Orchestration now lives in two places: the canvas the analyst draws, and the state machine it compiles into. Kept manageable by generating the second from the first.

6.5 — Compile in the web tier, deploy from somewhere else

Problem

When an analyst saves a pipeline, the drawing has to become something AWS can actually run — a state machine. Getting there is two separate operations:

Compiling turns the canvas into a state machine definition. The two are already the same shape: named boxes and arrows on one side, named steps and what-comes-next on the other. So this is translation, not interpretation, and it is pure computation — data in, data out, no AWS call anywhere.

Deploying is the call that turns that definition into a real, runnable thing in the account. It needs permission to create a state machine, and permission to attach an execution role to it.

The obvious implementation does both in the web tier, which hands the internet-facing server both of those permissions.

Chose

Split them along that seam. Saving compiles and registers a versioned plan; a separate privileged process, running under its own identity, deploys pending plans.

The internet-facing server should not hold permission to create infrastructure, because whoever compromises it inherits that permission. Attaching roles is the sharpest edge: anyone who can attach a role can potentially attach one more privileged than their own.

The analyst loses nothing. A broken diagram is still rejected in under a second, while they are looking at it. Compiling is the half that produces the value, and it is the half that needs no permissions at all.

How

The compiler is ordinary Python with no AWS libraries in it: canvas in, Amazon States Language out (the JSON dialect Step Functions reads). That is what makes it safe to run in the web tier, and it means it can be unit-tested offline.

Compiled plans are versioned into S3. A separate deployment script, run under its own more privileged identity, picks up pending plans and creates the state machines. The web tier's role simply does not include permission to do that.

Bonus

Every compiled version is retained rather than overwritten, with its hash and timestamp. That is the audit answer to "which calculation produced the number we filed?"

And because each pipeline compiles to its own state machine instead of being fed through one generic interpreter, the execution graph AWS shows you is the analyst's diagram. When a run fails, the console highlights the same box they drew. A generic interpreter would have moved the problem into AWS and lost that.

6.6 — Accepting a performance cost, then paying it back

Problem
After 6.1, a page that used to do twenty instant memory lookups was making twenty network calls. Validating a canvas of eleven steps cost twenty-one round trips to fetch three distinct records.
Chose

Remember records for the duration of a single request. Twenty-one round trips became two.

One request only, on purpose. A longer-lived cache brings staleness: one server showing an old version of a model another server just updated. Scoped this way the data is consistent within the operation and fresh on the next one.

How

No AWS service — a language feature. Python's contextvars, which the async runtime copies for each task. The web framework runs every request in its own task, so per-request isolation comes for free: concurrent requests cannot see each other's entries and nothing survives into the next one.

It lives in the storage module, so writes refresh it automatically and no caller can forget to invalidate it. Every hit returns a copy, so code that modifies what it got cannot corrupt the next reader. Misses are remembered too, because validation asks about the same missing reference over and over.

Worth stating plainly: a managed cache would have added a network hop to fix a problem caused by network hops.

Gave up
Within one long operation the data is a snapshot. For a workflow run that is arguably what you want anyway — the run should not see a model change underneath it halfway through.

6.7 — Designing for the query, not the storage

Problem
Listing recent runs meant reading every run ever recorded and sorting them, because records were organised by identifier and identifiers sort meaninglessly. The cost grew forever.
Chose
A secondary index organising the same records by function and time, so "the newest fifty" is a range read that stops after fifty. The cost of a page no longer depends on how many runs exist. Ten runs or ten million, the same.
How

A DynamoDB global secondary index: a second, automatically maintained view of the same records, keyed by function and timestamp instead of by id. Added in CDK, and DynamoDB backfills it.

Reads walk it newest-first and stop at the page size, returning a marker for the next page. That marker travels in an HTTP header, not the response body, so existing callers that expect a plain list carry on working.

Timestamps are stored as text in a format that sorts chronologically when sorted alphabetically. The whole index depends on that one property.

Gave up
Nothing on the read path. But it fixed only half the problem: making a read cheap says nothing about how much there is to read. Retention was a separate question with a separate answer, settled later — see §7.4.

6.8 — Protecting the records from the deployment that manages them

Problem
The records database was set to be deleted along with the stack that creates it. Sensible for a lab, wrong the moment the database holds an audit trail. And it is not only an explicit teardown that triggers it: any change the platform treats as a replacement destroys and recreates the table, taking the contents with it.
Chose
Retain the database independently of the stack, and enable point-in-time recovery — 35 days of second-granularity restore, the only defence against a bad write rather than a lost resource.
How
Two lines of infrastructure-as-code, deployed and then confirmed by querying the live database instead of trusting the deployment output. The same change covers the replacement case as well as deliberate teardown.
Gave up
A teardown now leaves an orphaned database to remove by hand. That is the correct direction to fail: recovering from an unwanted leftover is tedious, recovering from a deleted audit trail is impossible.
Note
This sat open longer than it should have. Everything built on top of that database assumed it mattered. The configuration said otherwise, and the gap between those two was the real risk.

6.9 — Keeping the record when the payload will not fit

Problem
The database caps a single record at 400 KB. A run carries its full result set, so an unusually large run exceeds that, and the write fails after the computation has already succeeded.
Options
Fail the request; silently truncate; or store the result elsewhere and link to it.
Chose
Keep the run record, drop the row-level detail, and note how many rows were omitted. The user still gets their complete results; only the stored copy is trimmed. Failing would throw away work that succeeded. Truncating silently would leave a record that lies.
How

Application logic, no service. Before writing, the record is measured; if it exceeds the limit the row-level results are dropped and a note recording how many rows were omitted is attached. The complete results still go back to the caller — only the stored history is trimmed.

Gave up
Full history for outsized runs. Storing the payload in object storage is the right long-term answer and is the next step if large runs become common — this is a deliberate, documented interim.

6.10 — Records are durable; so are the files

Problem
Moving the records to a database left the files — uploaded datasets, model artifacts — on the local disk of whichever server received the upload. That is worse than an obvious failure. The record appears everywhere, so the dataset shows up in every listing, and then reading it fails on every server but one.
Chose
Uploads write to object storage as well as local disk, and any server missing a file fetches it on demand and keeps a copy. A cache, not a direct read every time, because model files are read repeatedly during a run.
How

Amazon S3, with local disk demoted to a cache. Uploads write to both. Reads take the local file if it exists; if not, the file is fetched, saved locally, and used from there onwards.

The download lands under a temporary name and is then renamed into place, so a second reader never catches a half-written file. Model artifacts also trigger a listing of their folder, so the companion files come along.

Detail
Model artifacts need their companion files to load at all. Fetch the model without them and the error names a missing class, not a missing file, which is a confusing way to find out. So the fetch brings the companions with it.

6.11 — Measuring an upgrade, and shipping it turned off

Problem
The document search behind the AI agents used keyword matching. The obvious upgrade is semantic search using embeddings.
What happened

It was built, measured against a test set, and it lost. Keyword matching found the right document first every time. The semantic version managed three out of five.

Every document in the corpus describes deposit balance modelling, so every passage looks like every other one and semantic similarity has almost nothing to separate. Analysts also search using the corpus's own vocabulary, which is exactly where keyword matching is strongest.

Chose
Ship it switched off, one setting away, with the condition for revisiting written down: a larger, more varied corpus. That is exactly the regulatory-filings case, where many agencies across decades describe the same ideas in different words.
How

Amazon Bedrock for the embedding model, with vectors cached by content hash so re-indexing an unchanged document costs nothing. Results are combined with the existing keyword ranking, then both are measured against the same query set. The whole path sits behind one environment variable, which is what makes "built but off" a real state instead of a claim.

Caveat
Five queries, written by the same person who chose the expected answers. A defensible benchmark needs analyst-written queries with blind relevance labels. This was enough to decline an upgrade. It was not enough to call the question settled.

6.12 — Lambda now; containers when the constraints change

Chose
Lambda for computation. Runs are short, bursty and event-driven, and it costs nothing when idle.
How

AWS Lambda, running a container image so the scientific-computing libraries and the model files fit. AWS CodeBuild builds the image and Amazon ECR stores it, so no developer needs Docker locally. The image tag is a hash of the source, which gives "what exactly is running?" an answer.

Work reaches it from an SQS queue; AWS delivers messages to the function and scales it on queue depth. One image serves every job type, selected by a mode field in the message.

Revisit when

None of these is true yet, and any one of them would flip the decision: a single run passes fifteen minutes, which is Lambda's hard limit; the image passes ten gigabytes; a model needs more memory than Lambda offers, or a GPU; or cold-start latency stops being acceptable.

The migration would be contained. Step Functions invokes container tasks the same way it invokes Lambda, so the state machine design survives the change.

6.13 — Taking the password out of the request path

Problem

§6.3 stopped the application from storing sessions. It still had the application handling credentials: the browser posted a username and password to an endpoint here, which forwarded them to the identity service and passed the tokens back.

That works, and it quietly makes this codebase part of the credential boundary. Every log line, every exception handler, every piece of middleware anyone adds later sits on a path a password travels down. Nothing was wrong with the implementation. The exposure is structural, and the only way to remove it is to stop the password arriving at all.

Options
Keep proxying and be careful: audit the logging, scrub the traces, and review anything added near that route forever. Or send the browser to the identity provider's own page and never see the credential at all.
Chose

The hosted page. The browser goes to Cognito, authenticates there, and comes back with a single-use code that it exchanges for tokens itself. Nothing in the request path ever sees a password, which is a property of the design rather than a discipline anyone has to maintain.

How

Authorization code flow with PKCE. PKCE rather than a client secret for a structural reason, not a preference: the frontend is a static bundle on a CDN, so anything it ships can be read by anyone who opens developer tools. It cannot keep a secret. That is what a public client means.

So the proof of "I am the one who started this flow" is a random verifier generated for each login, of which only the SHA-256 hash is sent up front. A stolen code is useless without the verifier, and the verifier never leaves the tab.

The state parameter is round-tripped and checked. This is the easy half to skip, because skipping it breaks nothing visible. Without it, an attacker can feed a victim a code of their own and log them into the attacker's account — a login that succeeds. Failures that look like success are the ones to name out loud.

The configuration is fetched, not compiled in. The bundle is built once and served everywhere, but the pool and client ids are chosen by CloudFormation. A build-time constant would mean one build per environment, for values you cannot know at build time. So a small endpoint reports them, and it is unauthenticated on purpose: a client id is an identifier, the hosted domain is where the browser is about to be sent in plain sight, and a public client has no secret to leak.

Gave up

Two deliberate stops short of the destination, both recorded rather than glossed.

Multi-factor authentication is optional, not required. Required locks out every existing user until each one enrols, and this pool's only member is the person running the deploy. It is one word to change on the day there is more than one user to coordinate. Authenticator apps only, not SMS: SMS bills per message and is the weaker factor, which is why NIST stopped recommending it.

And the old username-and-password path is still enabled at the identity service. The infrastructure, the container image and the frontend bundle ship as three separate steps, so there is no instant at which all three change together; leaving it on made a broken hosted flow a rollback rather than a lockout. That hold has now expired in the useful sense — a real login has gone through the hosted flow, which is the evidence the rollback was insurance against needing. Until the switch is actually thrown, the headline property is true of this service and not enforced by the pool: nothing in the request path handles a password, and someone holding a username and password could still obtain a token directly.

Note
Verified first as far as was possible without a human at a browser: the hosted page serves for this client and challenge, an unregistered redirect address is rejected, the callback survives the CDN's history fallback, the configuration endpoint answers from the deployed containers, and MFA reads as available with authenticator apps enabled. A real login has since been completed through the flow on the deployed system, which is the one part of it no automated check could reach — and which converts the second "stop short" above from a deliberate hold into a pending one-line change.

7Meeting a regulator's expectations

The decisions above were made with these questions in mind.

7.1 Can you reproduce a filed number?

Every workflow version compiles to a plan that is never overwritten, kept with its hash and timestamp, and not deleted when the workflow is. Every run is recorded with its inputs, outputs and the scenario it ran under. Model artifacts are versioned in object storage.

7.2 Who approved this, and can you prove it?

The approval gate is a state in a state machine, not a convention. The execution history is the evidence, and it is produced automatically instead of assembled afterwards. The gate also enforces a real timeout: an approval nobody grants within twenty-four hours fails explicitly, instead of leaving a run in limbo.

7.3 What can each component do if compromised?

Permissions are scoped to intent, not convenience. The worker can write results and read model files. It cannot read the document corpus, which sits in the same bucket under a different prefix, so the boundary is the permission rather than the bucket. The internet-facing web tier holds no permission to create infrastructure at all. Components reach each other by role, never by stored credentials.

One credential cannot come from a role, because it belongs to a third party: the AI provider's API key. It used to sit in plaintext in a file beside the code, copied onto every machine that ran the application. It now lives in an encrypted parameter store and reaches the process at startup, so no secret sits on disk. On a developer's laptop that is most of the fix, not all of it: reading the parameter needs cloud credentials of its own, so it trades a plaintext key for a local profile.

The hosting step closed the rest, and the obvious description of how is wrong. It is not that the application now reads the parameter with better credentials. The container is never told where the parameter lives, so the secret-fetching code does not run at all. The container runtime pulls the value before the process starts and hands it over as an ordinary environment variable, using a role held by the platform rather than by the application.

The role the application runs under can reach the records database, the queue, the state machine, object storage, sign-in and the model endpoint. It has no permission to read the secret it is holding. The credential is delivered by an identity the process cannot impersonate, which is stronger than encrypting it at rest, and why this is the last word on the subject rather than another interim.

7.4 What is your retention policy?

Decided, and the decision is the interesting part. This was the open item on this page for some time, because it is a policy question rather than a technical one: does a run count as evidence, in which case nothing may ever be deleted, or as working scratch?

A run is scratch. The reasoning turns on what a filed number is actually rebuilt from. The dataset, the model artifact, the saved workflow and the compiled plan for the version that ran are all kept indefinitely, so a result stays reproducible long after the row that first reported it is gone. What expires is the transcript, not the evidence. Run history is a rolling ninety-day window, enforced by the database's own expiry mechanism, and one setting turns it to "never" on the day that judgement stops holding.

Object storage got the matching treatment, with one deliberate exception. Job results expire after thirty days; superseded dataset uploads after a hundred and eighty; build artifacts after ninety. Model artifacts are exempt from every rule — their older versions are the answer to §7.1, and expiring them would quietly convert "we can show which artifact produced this number" into "we can show it for a year". A control that decays on a timer is worse than one that was never claimed.

The honest limit. Expiry is best-effort: the database sweeps within days of the deadline, not on the second. So it bounds growth and is not an access control. Anything that must be unreadable at a deadline needs a different mechanism. It also applies only to runs recorded after it was switched on, which is why turning it on late cost nothing — existing records carry no expiry and were never at risk.

Two related gaps were closed earlier. The records database has point-in-time recovery enabled — 35 days of second-granularity restore — and its removal policy is RETAIN rather than DESTROY, so neither a stack teardown nor a change the platform treats as a replacement takes the records with it. The cost of RETAIN is an orphaned table to delete by hand, which is the correct direction to fail: recovering from an unwanted leftover is tedious, recovering from a deleted audit trail is impossible.

7.5 Is the connection encrypted, and can it be bypassed?

Yes, and no. The second half is the part usually left out. The platform is reached over HTTPS through a content delivery network, which supplies the certificate, and plain HTTP is redirected rather than served. That on its own is half an answer, because the load balancer behind it was still answering the same requests unencrypted to anyone who found its address. "Encryption is available" and "encryption is enforced" are different claims.

So the load balancer now refuses any request that did not arrive through the network. One distinction matters to anyone assessing this: it is a guard, not a boundary. The token it checks has to be a literal value in the configuration, so it stops direct access and casual scanning without being a secret. Making the origin genuinely unreachable means putting it on a private network, which costs real money for a gateway this design chose to avoid.

7.6 Where does the data live?

One region, deliberately. Nothing is replicated across regions, so there is no question about where a given record resides. Data residency requirements are met by choosing the region, not by configuring replication.

8What is built, and what is proved

This section used to be called "built versus designed", and the rename is the status update: nothing here is merely designed any more. The distinction that still earns its place is the other one — between what is deployed and what has been exercised — and the qualified rows are the interesting ones.

Four rows are qualified, and each for a different reason. Semantic document search is built, measured, and switched off — the measurement said keyword search won on this particular corpus, so shipping it enabled would have been shipping a slower answer. "Built and off for a recorded reason" is a different state from "not built", and collapsing the two is how a table like this stops being useful.

The authentication rows moved recently and in different directions. The hosted sign-in flow was carried on this table as "deployed, login unproven" until a real login was completed through it on the deployed system — which is what turned it green, and is worth noting as a case where the missing evidence was a person at a browser rather than any further work. MFA remains available and not enforced. The old password path remains enabled, and its row changed from "deliberate" to "unblocked" for the same reason: a completed login is the evidence that was gating its removal. A row that says "deployed" when it means "deployed and untried" is the failure this table exists to avoid.

The one thing this table cannot yet say. Signing in is now proved on the deployed system; the rest of the path an analyst walks — load a dataset, run an analysis through a model, publish a number — has been exercised in development and not in production. The remaining gap is smaller than it was and it is still the honest description of where this stands: every row being green is not the same claim as the product working end to end.

9Why this order

The sequence was not arbitrary, and the reasoning is itself an answer to how you approach a migration.

Guardrails first. Budgets, audit logging and least-privilege access before the first real API call — because retrofitting those is how cloud programmes acquire findings.

Then the things that make the application honest: real model access, real document storage. Each one demonstrable on its own.

Then computation off the request path, because that removed a user-visible failure mode without touching how the application stored anything.

Then state, in dependency order: records first, then the performance cost that created, then the files, then identity. Each step could be verified before the next one started.

Hosting last, on purpose. Running the web tier on several servers before its state left the process would have produced servers that disagree with each other. The unglamorous half had to go first. Once it was done, what remained was configuration rather than redesign.

10Cost

The deployed footprint runs at effectively zero:

  • DynamoDB — on-demand billing, within the always-free allowance
  • Lambda, SQS, Step Functions — within permanently-free tiers at this volume
  • S3 — pennies for the corpus and artifacts
  • Cognito — free below fifty thousand monthly active users
  • ECR — one worker image and two web images, which is what keeps it inside the free allowance

The one deliberate trade is in how many images each repository keeps, and the asymmetry is the decision rather than the number. A scikit-learn image is around 277 MB against a 500 MB allowance, so two worker tags already exceed it — the worker keeps one. The web repository keeps two.

The reasoning is what each failure costs. A bad worker image fails a solve, and a solve can be retried; recovery is rebuilding from a known-good source tree, which is acceptable because the image tag is a hash of that tree. A bad web image takes the whole application down, and the fix at that moment should be repointing at the previous tag rather than waiting out a rebuild. Paying a few cents for the second web tag and not for the second worker tag is the same judgement applied twice, in opposite directions.

The pattern worth naming: every service here bills on use, not on standing capacity. That was a selection criterion, not a happy accident.

11Questions I expect

Grouped by the kind of question, because each kind wants a different answer. A design question wants a trade-off. A depth question wants a number. A behavioural question wants one specific incident and how it ended.

How to use this section. Every answer points at something real in this document. An answer you cannot follow with "show me" is a story, not evidence. Where an answer would overclaim, it says what was actually proved instead — §8 collects those distinctions, and under questioning they are worth more than any of the successes.

The most likely follow-up to anything here is "how do you know?" Answers that survive it cite a measurement, a log line or a failure. Answers that do not should not be given.

Design questions

"Walk me through a system you designed."

Lead with the diagnosis, not the diagram. This system could not run on more than one server, and the reason was not how it was deployed. The application held its state in memory. That one distinction decided everything else: the fix was a data-design change, and hosting had to come last instead of first.

"How do you handle a long-running human approval?"

A durable state machine, not application code. Explain why: code that waits in-process needs a repair routine to clean up after restarts, and a control that needs cleaning up after is hard to evidence to an examiner.

Get ahead of the follow-up: what happens when nobody approves? The wait has a twenty-four hour limit wired to its own end state, so an abandoned run fails as an outcome instead of sitting in limbo. Every path ending explicitly is what removes the need for a sweeper to find orphans later.

"Why DynamoDB and not a relational database?"

Because the access patterns were known in advance and are trivial: fetch one record by id, list all records of a type, and list the newest N runs for one function. Nothing joins across types. A relational database would bill for an idle instance and buy flexibility this workload does not use.

Offer the limit before they ask for it. This is the right answer because the access patterns are known. The moment somebody wants an ad-hoc query — "every run that touched this dataset last quarter" — the design owes them a table scan or a new index. That is a real cost, not a detail. What softens it is that one module owns every read, so adding an index or exporting to something queryable is a change in one file.

What makes it defensible rather than just cheap: the second key on run records was added after measuring that listing recent runs read every run ever recorded. The index answers a question the application actually asked, which is the only good reason to have one.

"Walk me through what happens on one request."

The browser holds a signed token. The request reaches CloudFront, the only thing with a certificate. CloudFront forwards it to the load balancer with a shared header, and the load balancer refuses anything that arrives without it. One of two Fargate replicas takes it, and either will do, which is the whole point of the preceding work.

Inside the process: the token is checked against cached public keys, with no lookup anywhere. Handlers read through one storage module, which serves repeat reads from a per-request cache that lives in a contextvar and dies with the request. Anything long-running never happens here. It goes on a queue and the caller gets an acknowledgement.

Then volunteer the detail that matters: the request touches no local disk. That sentence was false until recently, and making it true is what the whole migration was.

"A container dies mid-request. What happens?"

That request fails and the caller retries. The load balancer stops sending traffic there after a failed health check, and the service starts a replacement. Nothing else is lost, because the container held nothing. That is the property the question is really testing.

The better case is the solve, not the web tier. A run in progress is not in the container at all. It is a message on a queue being handled by a worker, and if that worker dies the message reappears and is retried. After three failures it lands in a dead-letter queue instead of disappearing, so someone can look at it. A run inside an HTTP request, which was the original design, would have vanished with the process.

"One region, and how many availability zones? What is the real availability story?"

Be precise here instead of reassuring. The managed services — DynamoDB, S3, SQS, Step Functions, Cognito — are multi-AZ by construction, so the state tier survives losing a zone with nothing configured.

The web tier survives it too, and you should be able to say exactly why, because "two replicas" does not establish it on its own. Two copies in one zone are two copies of the same outage. The network has two availability zones with one public subnet in each — the load balancer requires two, which is what forces the second. The service asks for two tasks and sets no placement strategy, so the platform's default spread puts one in each zone. Losing a zone costs one task, and the load balancer stops sending it traffic.

What that does not cover: with two tasks in two zones, losing a zone means running at half capacity until a replacement starts. Surviving a zone loss and surviving it without degradation are different claims. Only the first is true here.

Region failure is not covered, on purpose. One region, nothing replicated across regions, which also happens to be the clean answer to the data-residency question. Multi-region for a handful of analysts means paying continuously for a scenario that has never happened to this workload, and putting the same records in two jurisdictions. If the requirement appeared, the real cost would not be infrastructure. It would be deciding which region wins a conflicting write.

"What is your recovery story if someone deletes the wrong thing?"

Three separate mechanisms, because they fail differently:

A bad write — point-in-time recovery on the records table, 35 days of second-granularity restore. This is the only one of the three that helps against corruption rather than deletion.

A lost resource — the table's removal policy is RETAIN, so neither tearing down the stack nor a change the platform treats as a replacement takes the records with it. The cost is an orphaned table to clean up by hand, which is the correct direction to fail.

A lost file — the bucket is versioned, and the lifecycle rules that expire old versions are prefix-scoped so that model artifacts are exempt from every one of them. Their old versions are the audit trail.

A bad deploy — two mechanisms, and they cover different halves. The service runs with a deployment circuit breaker set to roll back, so a new task definition whose containers never pass a health check reverts automatically rather than draining the healthy ones. And the web image repository retains two tags, so repointing at the previous image is available when the problem is not a failed health check but a working container that behaves wrongly — the case the circuit breaker cannot detect.

The worker repository keeps only one tag, and that asymmetry is deliberate rather than an oversight: a bad worker image fails a solve that can be retried, while a bad web image takes the application down. Recovery there is rebuilding from a known-good source tree, which works because the image tag is a hash of that tree.

"How would this scale to a thousand analysts?"

Take the tiers separately, because they answer differently.

The state tier needs nothing. On-demand DynamoDB, S3 and SQS absorb it, and the read path was built so page cost does not grow with history. This is the half that was expensive to build and is now free.

The web tier is a number. Two replicas becomes more replicas, because the process holds nothing. That is the entire return on the migration — and say plainly that it became true only after the state work, not because of any hosting choice.

The solver is where I would look first, and the constraint is not throughput. It is the fifteen-minute function ceiling. A thousand analysts running small solves scales fine. One analyst running a solve that grows past fifteen minutes does not, and no amount of concurrency helps. That is a migration to container tasks, and §6.12 already names the trigger conditions.

What breaks before any of that is the model sandbox. Third-party artifacts run in subprocesses on the web tier, which is a per-replica resource cost, and at that scale it belongs on the worker with everything else.

"Why not put API Gateway in front of it?"

Because it would be a second thing doing what the load balancer and the distribution already do between them, and it bills per request for the privilege. TLS, a stable front door and request routing all come from CloudFront, which is serving the frontend and is therefore already in the path.

It becomes the right answer the moment this stops being one browser application and becomes an interface other systems call: per-consumer throttling, API keys, usage plans. None of that is true yet, and adding it early would mean paying for an abstraction to solve a problem nobody has.

"Why CDK rather than CloudFormation?"

Correct the premise first, because accepting it concedes a distinction that does not exist. This is not CDK instead of CloudFormation. The stack definition never runs in the cloud. It is read locally to produce a template, and the account executes that template. The real question is why generate the template instead of writing it, and that one has a good answer.

Because it makes least privilege the easiest thing to do. Six grant calls — read-write on the table, send on the queue, start-execution on the state machine — expand into policies scoped to the exact resource, and the template ends up with thirteen IAM resources. Hand-writing those is exactly where security posture decays: writing the ARN of a queue that does not exist yet is tedious, a wildcard always works, and nobody comes back to tighten it. Every other benefit here is convenience. This one is a security property.

The convenience is real too. One network construct with four arguments emits eleven resources — subnets, route tables, routes, associations, gateway, attachment — that all have to stay consistent with each other. The five alarms come from one helper function with shared defaults, including the missing-data setting that separates five working alarms from five parked in an error state on an idle account. Written longhand, that setting has to be right five separate times.

And the secret wiring encodes knowledge instead of requiring you to remember it: attaching a parameter to a container grants read to the execution role, which is not the role the application runs as. §7.3 explains why that difference is the whole security property.

Then name what the abstraction cost, because an answer that only defends the choice is the weaker answer. It produced a bug raw CloudFormation cannot have. A value that reads as the account identifier is not a string at all. It is a placeholder resolved when the template is generated, and its numeric suffix is an index into the construct tree. So a secret derived from it silently changed whenever an unrelated resource was added, which caused slow deploys and a window where two components disagreed and refused real requests.

A hand-written template has no generation step, so nothing in one can look like a value while being a deferred reference. That is the tax. It was paid once, and it took reading the diff to find, not a failing test.

What follows from paying it: build the template twice and compare, as a check before deploying rather than a discovery afterwards. Recommending this tool means owning that class of bug.

When the answer flips. When the people maintaining it do not write Python or TypeScript — infrastructure its owners cannot change is worse than verbose infrastructure they can, and that outranks everything above. When the template is the artefact somebody signs off on in a change-approval process, because asking a reviewer to approve generated output nobody edits is a weaker review than it looks. And below roughly ten resources, where the toolchain costs more than it saves.

Depth questions — the ones that follow "how do you know?"

"How would you make this highly available?"

Be specific about what was actually blocking it. Ten record types moved to a managed database, uploaded files moved to object storage, and sessions became signed tokens that need no shared lookup.

Then say what the audit taught, because that is the more useful half. I twice claimed the state migration was finished before it was. Listing the module-level dictionaries, instead of trying to remember them, found six registries of analyst work still sitting in process memory. On a question this consequential the answer has to come from a search, not from memory.

Then be honest about the cost: reads became network calls, and a per-request cache was needed to pay that back. And be exact about what the finished version proves. The web tier runs as two replicas behind a load balancer, and the line to quote is not the successful request. It is the one both containers printed at startup: pulled 2 prebuilt index files, published 0. Two processes, no shared disk, same answer. That is the whole migration in one log line.

Then say what is still unproved, because the question invites overclaiming. Two replicas starting healthy, and a person signing in, are both smaller claims than an analysis running end to end on the deployed system. That has been done in development and not yet in production.

"How do you know it works?"

Separate the levels of evidence, because this project has all of them and they are not equal.

Tests for anything decidable offline. The canvas compiler has no AWS libraries in it exactly so it can be unit-tested, and the storage seam has a test written for the general pattern — "does a mutation persist?" — rather than for the specific places I had in mind. That test caught one I had not thought of: setting a warehouse connection's status and timestamp, and persisting neither.

Checks against live services for what tests cannot see, and this level found the most. Backups were confirmed by querying the live database instead of trusting the deployment output. The need for clock tolerance surfaced when a real token from the real pool was rejected as "not yet valid".

A human, for the part no automated check reaches. The hosted sign-in flow could be verified in pieces without a browser: the page serves, a bad redirect address is rejected, the configuration endpoint answers from the deployed containers. None of that adds up to a login. Completing one was the only way to close it, and that is now done.

Nothing at all for what is still open, and saying so is the point: no analysis has run end to end on the deployed system. It is listed in §8 rather than rounded up.

"How would you know it was broken at 3am?"

Alarms, not a dashboard, and the reasoning is the answer: a dashboard has to be visited, and nobody visits one at 3am. Five alarms, by email. Two of them exist because the states they watch are silent by design — a message landing in the dead-letter queue, and a function being throttled, both look like nothing happening.

Then volunteer the detail, because it is the mistake most alarm setups make. They treat missing data as breaching, not as insufficient. The default would park every alarm in INSUFFICIENT_DATA on a system that is idle most of the time, which looks like a broken alarm and teaches whoever sees it to ignore all five.

What is missing: none of this is a service-level objective, and there is no alarm on "a user got a slow response". Alarms on failure are the easy half.

"What does an attacker get if they compromise the web tier?"

Read and write on the records table, the ability to enqueue jobs and start executions, object access under the results prefix, sign-in operations, and model invocation. Not: any permission to create infrastructure, attach a role, or read the document corpus. The corpus sits in the same bucket under a different prefix, so the boundary is the permission, not the bucket.

The sharpest edge is role-passing, which is why §6.5 exists. Compiling a canvas into a state machine definition needs no permissions at all. Only deploying it does. Splitting there means the internet-facing process can produce a plan and cannot make it real.

And the credential an attacker most wants, the third-party model API key, is one the process cannot fetch. It is injected before the process starts, by an identity the process does not hold. Reading it means already being inside the container, not merely being able to make it do things.

"Why isn't all of your infrastructure declared in one place?"

Most of it is. One file describes the stack, and deleting a resource from it deletes it from the account. Two things sit outside, each for a different reason, and neither reason is that somebody forgot.

The object lifecycle rules, because the bucket predates the stack and is referenced rather than owned. Infrastructure-as-code can grant access to a resource it does not manage, but it cannot set properties on one. The alternatives were a small function-plus-role maintained forever to make a single API call, or adopting the bucket into the stack and putting the document corpus one policy mistake away from deletion.

The provider API key, because the template format has no encrypted-value type at all — and that is a deliberate refusal rather than a gap, since a template is a plaintext document that surfaces in the console, in change sets, and in every diff. Declaring the secret there would write it into precisely the places the exercise exists to keep it out of.

The general point: a secret whose value you did not generate can never originate in infrastructure code. Something has to carry it in from outside, exactly once. The only real question is which command does that, and whether the codebase says so out loud. Both scripts open by explaining why they are not part of the stack, so the next reader is not left wondering whether it was an oversight. A thin wrapper runs everything in dependency order when one command is genuinely wanted.

"How would you build search over thirty years of regulatory filings?"

The hard part is not similarity search. It is ingestion and trust: splitting documents along meaningful boundaries, attaching metadata you can filter on, citing sources so an answer can be audited, and choosing a vector store whose cost model matches an access pattern that is bursty and small.

Mention the measurement that said keyword search won on this corpus, and why a heterogeneous filings corpus is the case where that flips.

"When would you not use an AI model?"

For the numerical optimisation at the core of this platform. It is a deterministic calculation with a correct answer, it must be reproducible for a regulator, and a language model is worse at it in every dimension that matters. The agents explain results and help build pipelines; they do not compute the numbers.

The general line: a model is the wrong tool wherever the requirement is that the same input produces the same output, and that anyone can be shown why.

Leadership Principles — one incident each, with the outcome

Why rehearse these separately. A design question can be answered from the design. A behavioural question cannot. It wants one specific incident, the decision made inside it, and what happened afterwards. Each answer below is a real incident from this project, told in full here. §12 expands the three best ones.

The mistake to avoid: telling the story of the successful outcome. In every one of these, the useful content is the wrong turn before it.

Dive Deep — "tell me about a time you found a problem others missed."

I had twice written that the state migration was complete. It was not. Instead of trying to recall which registries had been moved, I searched the codebase for module-level dictionaries, and found six still holding analyst work in process memory: charts, Python tools, dashboard layouts, playbooks, analytic definitions, warehouse connections.

The transferable part is the method, not the finding. "Where does state live?" cannot be answered from memory, because the thing that breaks you is the thing you have forgotten. One search took about a minute and overturned a claim I had put in writing twice. I now treat any claim that something is complete as owing a search.

Outcome: the six were migrated, and the earlier claim was retracted in the document instead of quietly edited away. §6.3 still carries the correction, because a document that silently repairs its own errors teaches nobody anything.

Are Right, A Lot — "tell me about a time you were wrong."

Two, and they are different kinds of wrong.

Wrong about facts: the completeness claim above. The fix was procedural — enumerate, do not recall.

Wrong about a judgement: I built semantic document search before building the evaluation set to judge it. It lost. Keyword matching found the right document first every time; the embedding version managed three out of five. Every document in the corpus describes the same subject, so semantic similarity had nothing to separate on. A day spent defining the benchmark first would have reached the same answer before the effort was spent.

What I did with the losing result is the part worth telling. I shipped it switched off, one setting away, with the condition for revisiting written down. And I recorded the caveat: five queries written by the person who also chose the expected answers is enough to decline an upgrade, and not enough to call the question settled.

Invent and Simplify — "tell me about a time you simplified something."

Three items on the remaining list: the browser application had nowhere to be served from, the API was unencrypted, and cross-origin permissions were set up for a developer's laptop. Three items, three efforts, three different places.

They were one purchase. A content delivery network in front of the existing load balancer supplies a certificate the load balancer cannot have on its own, because certificates are issued against domain names and nobody owned the one it was given. The same network serves the compiled application. And it puts the application and the API on one address, which does not so much configure cross-origin permissions as delete the question.

The reason to look for that shape is not elegance. Three separate efforts would each have been justified on their own and wasteful together, and nothing in the three tickets would have shown it. Nobody would have noticed the waste.

The near-miss is the honest half. The obvious way to make bookmarked pages work is the network's "serve the main page when something is missing" setting, and it applies to everything, including the API. Genuine "no such record" answers would have come back as a page reporting success: a working application in front of an API that lies. The fix was a small function scoped to the frontend's traffic only.

Ownership — "tell me about a bug you could have fixed narrowly."

Saving a skill and deleting one had disagreed about the filename for as long as both existed. The writer kept hyphens; every lookup converted them to underscores. Skills are named in kebab-case by convention, so the two never matched, and deleting one reported it missing.

It had been harmless for months: a file nobody could delete through the interface, on a single server, in a folder that was empty in practice. Moving skills into shared storage changed that completely. A delete that cannot find its file also cannot remove the shared copy, and the next sync would faithfully restore what the user had just deleted.

A latent bug is not a small bug. It is a bug whose blast radius is set by what you later build on top of it. The narrow fix was to teach the delete path the other spelling. I wrote one naming function used by every writer and every lookup instead, plus a fallback so files written the old way are still removable. The filename had just become a storage key, and two conventions in that position generate defects forever.

Insist on the Highest Standards — "when did you refuse to accept 'it works'?"

The deployment wrapper had run clean twice. It broke on the first deploy that actually changed something, in two unrelated ways that had both been there since it was written. It read the deployment tool's output in the wrong encoding. And it asked the tool to prompt for confirmation on permission changes, which without a terminal makes the tool refuse outright — so every deploy touching permissions had been failing silently from automation.

Both bugs share a shape: a safeguard you have never seen fire is a safeguard you have never tested. The earlier runs survived only because the phrase "there were no differences" contains nothing but plain letters. A convenience layer exercised only on the no-op path has not been tested. It has been visited.

The same shape shows up in the lifecycle rules. On a versioned bucket, expiring an object only writes a deletion marker: the bytes stay, and stay billed, until a second rule expires the superseded versions. It is the most common way a lifecycle rule appears to work and does nothing, and the only way to catch it is to check the bucket rather than the configuration.

Frugality — "how did you keep the cost down?"

The deployed footprint runs at effectively zero, and that was a selection criterion, not an outcome. Every service in it bills on use rather than on standing capacity: on-demand DynamoDB, functions and queues inside permanently-free tiers at this volume, pennies of object storage, identity free below fifty thousand monthly users.

Two decisions where it actually bit, because a principle that never costs you anything is not a principle:

Two images, not one. Shipping one image everywhere would have worked, and would have made every cold start pull an image several times larger for the sake of one file. The worker image is already most of the registry's free allowance on its own.

And keeping one worker image while keeping two web images, which is the same judgement applied in opposite directions. A bad worker image fails a solve that can be retried. A bad web image takes the application down, so that one gets a rollback target and the few cents it costs.

Bias for Action — "when did you ship something incomplete?"

The hosted sign-in flow, twice over. MFA is optional rather than required, because required locks out every existing user until each one enrols, and this pool's only member is the person running the deploy. Requiring it is a fast way to be locked out of your own system. And the old password path is still enabled at the identity service, because the infrastructure, the container image and the frontend bundle ship as three separate steps. There is no instant when all three change together, so leaving it on made a broken flow a rollback rather than a lockout.

What makes this action rather than carelessness is that both are written down as stops short of the destination, each with the condition for closing it. The version that goes wrong is the one where the same two calls are made and nobody records that they were calls at all. Six months later they look like the design.

Earn Trust — "how do you handle being wrong in public?"

This document carries its own corrections instead of being edited to look consistent. §6.3 still contains the sentence saying an earlier version of this page was wrong about what blocked horizontal scaling. The build log records "two replicas are healthy", then records separately underneath that a person later signed in, instead of editing the first claim upward to look better.

A document that records only its successes is one nobody can learn from. And practically: a reader who catches one unmarked overclaim has to re-check everything else. Keeping the retraction visible is cheaper than being audited.

Deliver Results — "what actually shipped?"

Ten record types moved from process memory into a managed database, with a sparse index for run history. Uploaded files, model artifacts, skills and the search index moved to object storage. Sessions became signed tokens, and then sign-in moved off this service entirely. Computation moved off the request path onto a queue, with a worker and a dead-letter queue. Multi-step runs got a durable approval gate. The web tier runs as two container replicas behind a load balancer, fronted by a CDN that supplies TLS. Retention is decided and enforced in both the database and object storage. Five alarms. All of it inside the free tier.

And the sentence that should follow immediately: nobody has yet run an analysis end to end on the deployed system. Every capability is deployed. "The product works in production" is a claim I have not earned. Volunteering that is what makes the rest of the list credible.

"What would you do differently?"

Two things. The retention policy should have been decided before run history was stored, not after. It is a policy question that constrains the data model, and answering it late risks a migration.

It was answered late and cost nothing, and the reason is luck rather than foresight. The expiry mechanism is per-record and opt-in, so switching it on left every existing record untouched instead of demanding a backfill. Had the answer been "archive everything, delete nothing", the same delay would have meant moving years of records after the fact.

And the semantic search work should have started with the evaluation set rather than the implementation; building it first meant discovering it lost after the effort was spent, when a day defining the benchmark would have found the same answer sooner.

What this project is not evidence for. It is single-author work, so it shows nothing about hiring, developing or disagreeing with other engineers. An interviewer probing Hire and Develop the Best or Have Backbone, Disagree and Commit needs a story from somewhere else. Customer obsession is only partial too: the analyst-facing decisions here — failures explained as named causes instead of stack traces, validation while the diagram is still on screen — are reasoned from the domain, not from users who were asked. Claiming otherwise on the strength of this work would not survive one follow-up.

12Three things that went wrong

The build log ran to thirty-nine entries. These are the three worth telling out loud: one about depth, one about simplifying, and one that is the point of the whole project.

Why a design document carries its own failures. Several choices in §6 only make sense once you know what was tried first. And a document that records only its successes teaches the reader that everything went well, which is never the useful lesson.

1

A bug that was harmless for months, until it wasn't

Moving uploaded skills into shared storage should have been the easy half of the last migration step — the same pattern the datasets already used. The test I wrote to prove it worked failed on the first run, but not where I had pointed it.

3

The log line the whole migration was for

The first deploy of the web tier brought up two servers behind a load balancer. Both healthy, both answering in about two hundred milliseconds. Nothing failed, which was not the expectation — a container image that has never been run usually fails its first health check.

The interesting output was not the successful request. It was one line, printed identically by both servers as they started:

pulled 2 prebuilt index files, published 0

Neither server had ever built a search index, and neither needed to, because the other had already paid that cost and left the result where both could find it.

Why this is the whole argument in miniature. Without it, each server would have quietly fallen back to keyword search while it rebuilt. For those few minutes the same question would have returned different answers depending on which server answered it. No error, no alarm, nothing to search the logs for. Everything else in this project existed so that one line would be boring.

Being precise about what it proved. Two replicas ran, shared their stores, and agreed. That is "it starts and it is healthy", which is a different claim from "it is correct". A person has since signed in through the hosted flow, which exercises the whole chain — network, load balancer, container, identity service, token, authenticated requests. Running an analysis end to end on the deployed system has not been done yet, and §8 says so.
