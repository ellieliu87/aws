Terms used in this document
State machine
A workflow written down as data — a list of named steps and what comes after each one. AWS reads that definition and runs it, remembering where every execution has got to. Called a state machine because a running execution sits in exactly one step at a time and moves between them along defined transitions.
Step Functions
The AWS service that stores and runs state machines. It is what makes "wait for a person to approve this" survive a restart: the waiting belongs to the service, not to any running process.
Compile / deploy
Compiling turns the analyst's canvas into a state machine definition. It is pure computation — data in, data out, no AWS involved. Deploying is the call that turns that definition into a real, runnable thing in the AWS account. They need very different permissions, which is the point of §6.5.
Lambda
Runs a piece of code on demand without a server to maintain. You are billed per invocation, so idle costs nothing. Its constraint is a hard fifteen-minute ceiling per run.
Fargate
Runs a long-lived container without a server to maintain. Suited to something that must stay up and answer requests, where Lambda suits short bursts of work. This is where the web tier is designed to run — see §6.12 for when it becomes necessary.
Replica
One of several identical copies of the application running at the same time, so that one failing does not take the service down. Making more than one copy possible is what most of this document is about.
Queue / dead-letter queue
A queue holds work to be done later so the website does not have to wait for it. A dead-letter queue is where a message goes after it has failed several times — so failures are kept for inspection rather than silently discarded.
Token
The thing your browser sends with every request to prove who you are. The distinction that matters here: a token can be a reference the server must look up, or a signed document carrying the facts inside it. §6.3 is about moving from the first to the second.
Role
An identity a piece of software assumes to get permission to do something, instead of holding a stored username and password. "Passing a role" — attaching one to a resource you are creating — is a powerful permission, because whoever can pass roles can potentially attach one more privileged than they hold.
Cold start
The extra delay on the first request after a period of inactivity, while the environment is prepared. The price of paying nothing while idle.

1What the system does

The CMA Workbench is a self-service analytics platform for the analysts who produce a bank's capital-planning numbers — the deposit balance forecasts and net-interest-income projections that feed CCAR stress testing and the annual outlook.

Before a tool like this, that work is spreadsheets and one-off scripts. The workbench gives an analyst four things in one place:

  • Data — connect to a warehouse table or upload a file, and see its schema and sample rows immediately.
  • Models — register an existing model artifact, or train a regression in the browser against bound data.
  • Workflows — draw a pipeline on a canvas (data → transform → model → output), run it, and download the result.
  • Agents — ask questions in plain language, with AI agents that can read the datasets, models, and runs the analyst is looking at.

The characteristic that drives the architecture: the numbers this produces get filed with a regulator. That single fact shaped more of the design than any performance requirement did.

2Why it needed re-architecting

The original build kept everything it knew in the memory of one running process — every dataset, every registered model, every completed run, every logged-in user's session.

Three consequences followed, and the third is the one that matters:

  1. Restarting lost work. Deploy a fix on Friday afternoon and every dataset an analyst uploaded that week was gone.
  2. It could not scale. Adding a second server would not help, because the two servers would disagree about reality — a dataset uploaded to one was invisible to the other.
  3. There was no durable record of what happened. If a regulator asked "which calculation produced this number?", the honest answer was that the evidence lived in a process that had since restarted.

The diagnosis matters more than the symptoms. This was not a deployment problem. There is no amount of load balancing, auto-scaling, or containerisation that fixes a process which holds its own truth. It was a data design problem, and it had to be solved as one before any hosting change would mean anything.

That is the thesis of this architecture, and the reason the work happened in the order it did.

3Principles applied throughout

Five rules shaped every decision that follows.

Fix the data design before the hosting

Moving state out of the process is what makes a second server meaningful. Doing it in the other order produces servers that disagree with each other — worse than one honest server.

Every AWS dependency is optional

Each integration checks for its configuration and falls back to the original local behaviour when absent. A developer with no AWS account runs the full application. This is not developer convenience for its own sake: it means the fallback path is exercised constantly, so it still works when it is needed, and the system stays testable without a cloud account.

Prefer managed services with no idle cost

This is a system used by a handful of analysts in bursts. Anything billing a standing capacity floor is the wrong shape, regardless of its technical merits.

Make the audit trail a property of the design, not a feature

Versioned artifacts, retained execution history, and immutable compiled plans are cheaper to build in from the start than to add under regulatory pressure.

Say plainly what is built and what is designed

Section 8 lists both. A design document that blurs the two is not usable by anyone.

4How the platform works

Two distinct paths through the system, with different requirements.

The interactive path

An analyst clicks something; the answer comes back immediately. Browsing datasets, previewing data, editing a chart, talking to an agent. These are short, chatty, and latency-sensitive — including agent responses, which stream back token by token over a held-open connection.

The workflow engine

An analyst draws a pipeline on a canvas and runs it. This is the heart of the product, and it works like this:

  1. Validate before running. The canvas is checked for problems while the diagram is still on screen — circular dependencies, a model whose input is missing, a model expecting a column the upstream data does not have. Fixing a broken pipeline is far cheaper before it runs than after.
  2. Work out the order. The pipeline is a dependency graph, so the engine sorts it into an execution order and rejects anything circular.
  3. Resolve the inputs. Each step's input is assembled from what feeds it — a scenario, an uploaded dataset, a warehouse table, or the output of an earlier model.
  4. Run each model in isolation. Model artifacts are third-party code. They execute in a separate sandboxed process with a time limit, so a model that hangs or crashes cannot take the platform down with it.
  5. Record every run. Inputs, outputs, timing, status, and the scenario context are all retained.
  6. Write the outputs. Results go to a CSV download or a warehouse table. Where several models feed one output — three deposit models feeding a net-interest-income calculator, for instance — their results are merged and labelled by source.
  7. Explain failures in the analyst's language. Failures are classified into named causes with a plain-English hint (FEATURE_MISMATCH, DQC_FAILED, TIMEOUT) rather than surfacing a stack trace. An analyst who can read the error can usually fix it themselves.

Analysts can save named pipelines and reload them. The in-progress canvas also survives a browser reload independently, so switching tabs never loses work.

How the records are organised

What code runs where

The services above say what is running. This says which code is running on each of them — a different question, and the one that decides how the repository is packaged.

Application code is not stored the way records are. It is built into an image, the image is kept in the container registry, and a compute service runs it. So "where does this folder live in the cloud" has two answers that are easy to conflate: the registry is where it lives, and the compute service is where it runs.

The shape worth noticing: two images, not one. The obvious approach ships one image everywhere, and it would work — the worker would simply ignore the code it does not call. What it would cost is size. The worker image carries the numerical stack because it unpickles real model artifacts, and it is already most of the registry's free allowance on its own; folding in the web framework, the agent runtime and the domain packs would push every cold start to pull an image several times larger for the sake of one file. Two images means each contains what it actually runs.

And one thing that is not in either image: the models themselves. An uploaded artifact is never deployed as code. It is data in object storage, fetched by the worker at invocation time and named in the payload — which is why adding a model requires no deploy, and why every workflow step invokes the same single function rather than one function per model.

Nor is anything an analyst creates. Uploaded skills and the built search index used to sit on the disk of whichever server happened to receive them, which is the one thing that would have made a second replica genuinely dangerous — not a failure, but two servers answering the same question differently, with nothing anywhere reporting a problem. Both now live in object storage, and each server keeps a local copy it reconciles: at startup, and for skills on a short interval afterwards, since a skill is found by listing a folder rather than by name and a missing one raises nothing. That was the last thing tying a request to a particular machine.

The same service, two opposite answers. §6.12 argues that the solver should stay on functions rather than containers, and that remains true — solves are short and bursty and scale to zero. The web tier above reaches the opposite conclusion about the same service, because it is a long-lived process serving requests. Both are in this document, and reading one as the answer to the other is the easiest mistake to make here.

6Design decisions and trade-offs

Each decision states the problem, the options considered, what was chosen, how it was actually built, and what was given up.

Three of these needed no AWS service at all. 6.6 is a language feature, 6.9 is twenty lines of application logic, and 6.5 is deliberately less AWS than the obvious implementation. Reaching for a service is a choice like any other, and the How row says plainly when the answer was to not reach for one.

6.1 — Externalising state before changing the hosting

Problem
The application could not run as more than one copy.
Options
Add sticky sessions at the load balancer so each user always returns to the same server; or move the state out of the process.
Chose
Move the state out. Sticky sessions would have hidden the problem rather than solved it — a server restart still loses that user's work, and one overloaded server cannot shed load to another.
How

Amazon DynamoDB, reached through one module that exposes four operations — get, put, delete, list — over plain dictionaries. Each registry gained matching accessors in place of its dictionary.

Deliberately one seam rather than scattered database calls: it is the only place that knows storage exists, which is what made the per-request cache in 6.6 and the index in 6.7 possible without touching any caller. With no table configured it falls back to an in-process dictionary, so the original behaviour is still a code path that runs.

Gave up
Reads that used to be instant memory lookups became network calls. That cost was real and had to be paid back — see 6.6.

6.2 — One table, not one per record type

Problem
Four kinds of record needed durable storage.
Chose
A single table, where each record's key is its type plus its id. Fewer things to provision, monitor and back up. The alternative — four tables — buys separation the application does not need, since nothing queries across types.
How

One DynamoDB table declared in AWS CDK, so the infrastructure is version-controlled alongside the application. Records are grouped by type and identified by id within it — see the diagram in §5. On-demand billing, so an idle system bills nothing.

Gave up
It is less immediately obvious to someone browsing the console. A diagram and this document are the mitigation.

6.3 — Stateless tokens instead of a shared session store

Problem

Sessions lived in one server's memory, so a second server rejected tokens the first one issued.

An earlier version of this document called this "the last thing preventing horizontal scaling". That was wrong, and the correction is instructive: six further registries still held analyst-created work in memory — charts, Python tools, dashboard layouts, playbooks, analytic definitions, warehouse connections. Auth was simply the one that would have broken every request rather than a feature.

The lesson is about how to audit this class of problem. "Where does state live?" has to be answered by enumeration, not recollection — one search for module-level dictionaries found all six in about a minute, after I had twice asserted otherwise.

Options
Move sessions to a shared store (a database or a cache), or stop needing a session lookup at all.
Chose

The second. A Cognito token is signed and carries the user's identity, role, department and group memberships inside it. Any server verifies it mathematically against Cognito's public keys — no lookup, so nothing to share.

A shared session store is still a shared dependency: another thing to scale, another thing whose outage is an outage. Verification needs nothing but the token and a cached public key.

How

Amazon Cognito holds the users and issues the tokens. The application verifies them itself: it fetches the pool's public keys once, caches them, and checks each token's signature, expiry, issuer, audience and type on every request.

Job titles and department ride along as custom attributes on the user; group membership arrives as a standard claim and feeds the existing permission filter unchanged. Sixty seconds of clock-skew tolerance, because a token minted a moment ago can look fractionally future-dated to a machine whose clock differs — found the hard way, on the real pool.

Gave up

A signed token cannot be un-signed. Signing a user out revokes their ability to obtain new tokens, but the one already in their browser stays valid until it expires. The mitigation is a one-hour lifetime, which makes the expiry window the revocation window.

A revocation denylist would close that gap and would also reintroduce exactly the shared lookup this design removed. If the requirement were immediate revocation — plausible for a privileged-access system — the denylist would be correct, and the cost accepted deliberately rather than by default.

6.4 — Human approval as a durable state, not application code

Problem
Model governance requires a person to review results before they are published — the champion/challenger gate. Implemented in application code, the process must stay alive while it waits, which could be hours or days. A restart mid-wait strands the run, requiring a repair routine to detect and clean up the wreckage afterwards.
Chose

Move the sequence out of application code and into a state machine — a workflow written down as data, which AWS runs on your behalf, remembering where each execution has got to. "Wait for a human" becomes one of its steps, so the execution parks and holds until the reviewer answers, surviving restarts and deployments.

The approval gate is a control. A control implemented as a convention that a repair routine cleans up after is difficult to evidence to an examiner. A control implemented as a state machine has an execution history showing who approved what and when.

How

AWS Step Functions, using its wait-for-callback pattern. When the execution reaches the gate it hands out a one-time token and stops — consuming nothing while it waits. The approval endpoint returns that token, and the execution resumes from exactly where it paused.

A twenty-four hour limit on the wait, with the expiry wired to its own explicit end state rather than left to time out silently.

Gave up
Orchestration logic now lives in two places conceptually — the canvas the analyst draws, and the state machine it compiles into. Managed by generating the second from the first.

6.5 — Compile in the web tier, deploy from somewhere else

Problem

When an analyst saves a pipeline, the drawing has to become something AWS can actually run — a state machine. Getting there is two separate operations:

Compiling translates the canvas into a state machine definition. The two are the same shape already — named boxes and arrows on one side, named steps and what-comes-next on the other — so this is translation, not interpretation. It is pure computation: data in, data out, no AWS call anywhere.

Deploying is the call that turns that definition into a real, runnable thing in the account. It needs permission to create a state machine, and permission to attach an execution role to it.

The obvious implementation does both in the web tier, which hands the internet-facing server both of those permissions.

Chose

Split them along that seam. Saving compiles and registers a versioned plan; a separate privileged process, running under its own identity, deploys pending plans.

The web tier should not hold permission to create infrastructure, because that permission is what an attacker who compromises it inherits — and attaching roles is the sharpest edge of it, since whoever can attach roles can potentially attach one more privileged than they hold.

Nothing is lost on the analyst's side: a broken diagram is still rejected in under a second, while they are looking at it. Compiling is the half that produces the user-facing value, and it is the half that needs no permissions at all.

How

The compiler is ordinary Python with no AWS libraries at all — canvas in, Amazon States Language (the JSON dialect Step Functions reads) out. That is what makes it safe to run in the web tier, and it is unit-testable offline.

Compiled plans are versioned into S3. A separate deployment script, run under its own more privileged identity, picks up pending plans and creates the state machines. The web tier's role simply does not include permission to do that.

Bonus

Every compiled version is retained rather than overwritten, with its hash and timestamp. That is the audit answer to "which calculation produced the number we filed?"

And because each saved pipeline compiles to its own state machine rather than being fed through one generic interpreter, the execution graph AWS shows you is the analyst's diagram. When a run fails, the console highlights the same box they drew. The generic alternative would have moved the interpreter from application code into AWS and lost that.

6.6 — Accepting a performance cost, then paying it back

Problem
After 6.1, a page that previously did twenty instant memory lookups now made twenty network calls. Validating a canvas of eleven steps cost twenty-one round trips for three distinct records.
Chose

Remember records for the duration of a single request. Twenty-one round trips became two.

Scoped to one request deliberately: a longer-lived cache introduces staleness, where one server shows an old version of a model another server just updated. Scoped this way, the data is internally consistent for the operation and fresh on the next one.

How

No AWS service — a language feature. Python's contextvars, which the async runtime copies for each task. The web framework runs every request in its own task, so per-request isolation comes for free: concurrent requests cannot see each other's entries and nothing survives into the next one.

It lives in the storage module, so writes refresh it automatically and no caller can forget to invalidate. Every hit is a copy, so code that modifies what it received cannot corrupt the next reader. Misses are remembered too — validation asks about the same missing reference repeatedly.

Worth stating plainly: a managed cache would have added a network hop to fix a problem caused by network hops.

Gave up
Within one long-running operation the data is a snapshot. For a workflow run that is arguably the property you want: the run should not observe a model changing underneath it halfway through.

6.7 — Designing for the query, not the storage

Problem
Listing an analyst's recent runs meant reading every run ever recorded and sorting them, because the records were organised by identifier — which sorts meaninglessly. Cost grew forever.
Chose
A secondary index organising the same records by function and time, so "the newest fifty" is a direct range read that stops after fifty. The cost of a page no longer depends on how many runs exist — ten runs or ten million, the same.
How

A DynamoDB global secondary index — a second, automatically maintained view of the same records, keyed by function and timestamp instead of by id. Added in CDK; DynamoDB backfills it.

Reads walk it newest-first and stop at the page size, returning a continuation marker for the next page. That marker travels back in an HTTP header rather than in the response body, so existing callers that expect a plain list are unaffected.

Timestamps are stored as text in a format that sorts chronologically when sorted alphabetically — which is the property the whole index depends on.

Gave up
Nothing, on the read path. But it fixed only half the problem, and the half it left is worth separating out: making a read cheap says nothing about how much there is to read. Retention was a distinct question with a distinct answer, settled later — see §7.4.

6.8 — Protecting the records from the deployment that manages them

Problem
The records database was configured to be deleted along with the stack that creates it. That is a sensible default for a lab and the wrong one the moment the database holds an audit trail — and it is not only an explicit teardown that triggers it: any change the platform decides is a replacement destroys and recreates, taking the contents.
Chose
Retain the database independently of the stack, and enable point-in-time recovery — 35 days of second-granularity restore, the only defence against a bad write rather than a lost resource.
How
Two lines of infrastructure-as-code, deployed and then confirmed by querying the live database rather than trusting the deployment output. The same change also covers the replacement case, not just deliberate teardown.
Gave up
A teardown now leaves an orphaned database to remove by hand. That is the correct direction to fail: recovering from an unwanted leftover is tedious, recovering from a deleted audit trail is impossible.
Note
This sat outstanding for longer than it should have. Everything built on top of that database assumed it mattered; the configuration said otherwise, and the gap between those two was the actual risk.

6.9 — Keeping the record when the payload will not fit

Problem
The database caps a single record at 400 KB. A run carries its full result set, so an unusually large run exceeds it — and the write fails after the computation has already succeeded.
Options
Fail the request; silently truncate; or store the result elsewhere and link to it.
Chose
Keep the run record, drop the row-level detail, and annotate it with how many rows were omitted. The user still receives their complete results; only the historical copy is trimmed. Failing would discard work that succeeded; silently truncating would produce a record that lies.
How

Application logic, no service. Before writing, the record is measured; if it exceeds the limit the row-level results are dropped and a note recording how many rows were omitted is attached. The complete results still go back to the caller — only the stored history is trimmed.

Gave up
Full history for outsized runs. Storing the payload in object storage is the right long-term answer and is the next step if large runs become common — this is a deliberate, documented interim.

6.10 — Records are durable; so are the files

Problem
Moving the records to a database left the files — uploaded datasets, model artifacts — on the local disk of whichever server received the upload. This is worse than an obvious failure: the record appears everywhere, so the dataset shows in every listing, and then reading it fails on every server except one.
Chose
Uploads write to object storage as well as local disk, and any server missing a file fetches it on demand and keeps a local copy. A cache rather than direct reads every time, because model files are read repeatedly during a run.
How

Amazon S3, with local disk demoted to a cache. Uploads write to both. Reads take the local file if it exists; if not, the file is fetched, saved locally, and used from there onwards.

The download lands under a temporary name and is renamed into place, so a second reader never catches a half-written file. Model artifacts additionally trigger a listing of their folder so the companion files come along.

Detail
Model artifacts depend on companion files to load at all. Fetching the model without them fails with an error naming a missing class, not a missing file — a confusing way to discover the problem. The fetch brings the companions along.

6.11 — Measuring an upgrade, and shipping it turned off

Problem
The document search behind the AI agents used keyword matching. The obvious upgrade is semantic search using embeddings.
What happened

It was built, measured against a test set — and it lost. Keyword matching found the right document first every time; the semantic version managed three out of five.

Every document in the corpus describes deposit balance modelling, so every passage resembles every other and semantic similarity has almost nothing to separate. Meanwhile analysts search using the corpus's own vocabulary, which is precisely where keyword matching is strongest.

Chose
Ship it switched off, one setting away, with the condition for revisiting written down: a larger, more varied corpus. Which is exactly the regulatory-filings case, where many agencies across decades describe the same concepts in different words.
How

Amazon Bedrock for the embedding model, with vectors cached by content hash so re-indexing an unchanged document costs nothing. Results combined with the existing keyword ranking, then both measured against the same query set. The whole path is behind a single environment variable, which is what makes "built but off" a real state rather than a claim.

Caveat
Five queries, written by the same person who chose the expected answers. A defensible benchmark needs analyst-written queries with blind relevance labels. The measurement was enough to decline an upgrade, not enough to call the question settled.

6.12 — Lambda now; containers when the constraints change

Chose
Lambda for computation. Runs are short, bursty and event-driven, and it costs nothing when idle.
How

AWS Lambda, running a container image so the scientific-computing libraries and the model files fit. The image is built by AWS CodeBuild and stored in Amazon ECR — no developer needs Docker locally, and the image tag is a hash of the source, so "what exactly is running?" has an answer.

Work reaches it from an SQS queue; AWS delivers messages to the function and scales it on queue depth. One image serves every job type, selected by a mode field in the message.

Revisit when

Any of these becomes true, and none is yet: a single run exceeds fifteen minutes (Lambda's hard limit); the container image exceeds ten gigabytes; a model needs more memory than Lambda provides, or a GPU; or cold-start latency stops being acceptable.

The migration is contained: Step Functions invokes container tasks with the same pattern it invokes Lambda, so the state machine design survives the change.

7Meeting a regulator's expectations

The decisions above were made with these questions in mind.

7.1 Can you reproduce a filed number?

Every workflow version compiles to an immutable plan, retained with its hash and timestamp — never overwritten, and not deleted when the workflow is. Every run is recorded with its inputs, outputs, and the scenario context it ran under. Model artifacts are versioned in object storage.

7.2 Who approved this, and can you prove it?

The approval gate is a state machine state, not a convention. The execution history is the evidence, produced automatically rather than assembled after the fact. It also enforces a real timeout — an approval nobody grants within twenty-four hours fails explicitly, rather than a run sitting in limbo.

7.3 What can each component do if compromised?

Permissions are scoped to intent, not convenience. The compute worker can write results and read model files — not the document corpus, which lives in the same bucket under a different prefix. The internet-facing web tier holds no permission to create infrastructure at all. Access between components is by role, never by stored credentials.

The exception used to be the one credential that cannot come from a role, because it belongs to a third party: the AI provider's API key, which sat in plaintext in a file beside the code and was copied onto every machine that ran the application. It now lives in an encrypted parameter store and is read into the process at startup, so no secret material sits on disk. That is most of the fix rather than all of it — reading the parameter still needs cloud credentials of its own, so on a developer's laptop it trades a plaintext key for a local profile. The remainder closes with the hosting step, where the container's own role supplies the parameter and the application stops fetching anything at all.

7.4 What is your retention policy?

Decided, and the decision is the interesting part. This was the open item on this page for some time, because it is a policy question rather than a technical one: does a run count as evidence, in which case nothing may ever be deleted, or as working scratch?

A run is scratch. The reasoning turns on what a filed number is actually reconstructed from. The dataset, the model artifact, the saved workflow, and the immutable compiled plan for the version that ran are all retained indefinitely — so a result stays reproducible long after the row that first reported it is gone. What expires is the transcript, not the evidence. Run history is therefore a rolling ninety-day window, enforced by the database's own expiry mechanism, and configurable to "never" by a single setting on the day that judgement stops holding.

Object storage got the matching treatment, with one deliberate exception. Job results expire after thirty days; superseded dataset uploads after a hundred and eighty; build artifacts after ninety. Model artifacts are exempt from every rule — their older versions are the answer to §7.1, and expiring them would quietly convert "we can show which artifact produced this number" into "we can show it for a year". A control that decays on a timer is worse than one that was never claimed.

The honest limit. Expiry is asynchronous and best-effort — the database sweeps within days of the deadline, not on the second. That makes it a mechanism for bounding growth and emphatically not an access control; anything that must be unreadable at a deadline needs a different mechanism. It also applies only to runs recorded after it was switched on, which is why turning it on late cost nothing: existing records carry no expiry and were never at risk.

Two related gaps were closed earlier. The records database has point-in-time recovery enabled — 35 days of second-granularity restore — and its removal policy is RETAIN rather than DESTROY, so neither a stack teardown nor a change the platform treats as a replacement takes the records with it. The cost of RETAIN is an orphaned table to delete by hand, which is the correct direction to fail: recovering from an unwanted leftover is tedious, recovering from a deleted audit trail is impossible.

7.5 Is the connection encrypted, and can it be bypassed?

Yes, and no — and the second half is the part usually left out. The platform is reached over HTTPS through a content delivery network, which supplies the certificate; plain HTTP is redirected rather than served. That alone would have been half an answer, because the load balancer behind it was still answering the same requests unencrypted to anyone who found its address. "Encryption is available" and "encryption is enforced" are different claims.

So the load balancer now refuses any request that did not arrive through the network — it returns a refusal to everything else. Stated precisely, because the distinction matters to anyone assessing it: this is a guard, not a boundary. The token it checks has to be a literal value in the configuration, so it stops direct access and casual scanning without being a secret. Making the origin genuinely unreachable requires putting it on a private network, which costs real money for a gateway this design deliberately avoided.

7.6 Where does the data live?

One region, deliberately. Nothing is replicated across regions, so there is no question about where a given record resides. Data residency requirements are met by choosing the region, not by configuring replication.

9Why this order

The sequence was not arbitrary, and the reasoning is itself an answer to how to approach a migration.

Guardrails first. Budgets, audit logging and least-privilege access before the first real API call — because retrofitting those is how cloud programmes acquire findings.

Then the things that make the application honest — real model access, real document storage — each independently demonstrable.

Then computation off the request path, because that removed a user-visible failure mode without touching how the application stored anything.

Then state, in dependency order: records first, then the performance cost that created, then the files, then identity. Each step was verifiable before the next began.

Hosting last, and deliberately so. Running the web tier on multiple servers before its state left the process would have produced servers that disagree with each other. The unglamorous half had to go first — and having finished it, the remaining work is configuration rather than redesign.

10Cost

The deployed footprint runs at effectively zero:

  • DynamoDB — on-demand billing, within the always-free allowance
  • Lambda, SQS, Step Functions — within permanently-free tiers at this volume
  • S3 — pennies for the corpus and artifacts
  • Cognito — free below fifty thousand monthly active users
  • ECR — one image retained, which is what keeps it inside the free allowance

The one deliberate trade: keeping a single container image means there is no previous image to roll back to. Recovery is rebuilding from a known-good source tree, which is acceptable because the image tag is a hash of that tree. Retaining two costs a few cents a month and buys instant rollback — a reasonable thing to change, and a decision rather than an oversight.

The pattern worth naming: every service here bills on use, not on standing capacity. That was a selection criterion, not a happy accident.

11Questions I expect

"Walk me through a system you designed."

Lead with the diagnosis, not the diagram. This system could not run on more than one server, and the reason was not how it was deployed — it was that the application held its state in memory. That distinction determined everything else: it meant the fix was a data-design change, and it meant hosting had to come last rather than first.

"How would you make this highly available?"

Be specific about what was actually blocking it. Ten record types moved to a managed database, uploaded files moved to object storage, and sessions became signed tokens that need no shared lookup.

Then say what the audit itself taught, because it is the more useful half: I twice claimed the state migration was finished before it was. Enumerating the module-level dictionaries — rather than recalling them — found six registries of analyst-created work still in process memory. On a question this consequential, the answer has to come from a search, not from memory.

Then be honest about what that cost — reads became network calls, which needed a per-request cache to pay back — and what remains: the web tier still runs as a single process, and that step is now configuration rather than redesign.

"How do you handle a long-running human approval?"

A durable state machine, not application code. Explain why: code that waits in-process needs a repair routine to clean up after restarts, and a control that needs cleaning up after is hard to evidence to an examiner.

"How would you build search over thirty years of regulatory filings?"

The interesting part is not similarity search — it is ingestion and trust: splitting documents along meaningful boundaries, attaching metadata that can be filtered, citing sources so an answer can be audited, and choosing a vector store whose cost model matches an access pattern that is bursty and small.

Mention the measurement that said keyword search won on this corpus, and why a heterogeneous filings corpus is the case where that flips.

"Why isn't all of your infrastructure declared in one place?"

Most of it is — one file describes the stack, and deleting a resource from it deletes it from the account. Two things sit outside, and the useful answer is that each is outside for a different reason, neither of which is that somebody forgot.

The object lifecycle rules, because the bucket predates the stack and is referenced rather than owned. Infrastructure-as-code can grant access to a resource it does not manage, but it cannot set properties on one. The alternatives were a small function-plus-role maintained forever to make a single API call, or adopting the bucket into the stack and putting the document corpus one policy mistake away from deletion.

The provider API key, because the template format has no encrypted-value type at all — and that is a deliberate refusal rather than a gap, since a template is a plaintext document that surfaces in the console, in change sets, and in every diff. Declaring the secret there would write it into precisely the places the exercise exists to keep it out of.

The generalisable point: a secret whose value you did not generate can never originate in infrastructure code. Something has to carry it in from outside, exactly once. The only real question is which command does that, and whether the codebase says so out loud — both scripts open by explaining why they are not part of the stack, so the next reader is not left wondering whether it was an oversight. A thin wrapper runs everything in dependency order for the cases where one command is genuinely wanted.

"When would you not use an AI model?"

For the numerical optimisation at the core of this platform. It is a deterministic calculation with a correct answer, it must be reproducible for a regulator, and a language model is worse at it in every dimension that matters. The agents explain results and help build pipelines; they do not compute the numbers.

"What would you do differently?"

Two things. The retention policy should have been decided before run history was stored rather than after — it is a policy question that constrains the data model, and answering it late risks a migration.

It was eventually answered late and cost nothing, which is worth saying only because the reason is luck rather than foresight: the expiry mechanism is per-record and opt-in, so switching it on left every existing record untouched instead of demanding a backfill. Had the answer been "archive everything, delete nothing", the same delay would have meant moving years of records after the fact.

And the semantic search work should have started with the evaluation set rather than the implementation; building it first meant discovering it lost after the effort was spent, when a day defining the benchmark would have found the same answer sooner.

12What went wrong along the way

Section 6 says what was chosen. This says what it cost to find out — the failures, in the order they happened, with what each one taught.

Why this is in the document. A design that only records its successes is a design nobody can learn from, and several decisions in §6 are only defensible once you know what was tried first. Two entries below are corrections to claims made earlier on this page.

Setting up the account

01

Guardrails before the first API call

An administrator identity with multi-factor authentication, the root account locked away, two budget alerts, and audit logging on — all before writing a line of integration code.

LessonAccess to billing information is a separate switch that only the root account can flip. An administrator without it gets refused on budgets despite holding full permissions everywhere else. Cloud governance is not one dial.

02

A comma that would have silently disabled everything

BrokeTwo settings landed on one line of a configuration file, so the value of the first became the whole rest of the line. The check against it failed quietly, and the application would have carried on using the old provider while appearing configured for the new one.

LessonThe nastiest class of configuration bug: no error, no crash, just the wrong system answering. It argues for a startup check that the setting which was resolved matches the one that was requested.

Getting the AI models working

03

The seam already existed

Adding a third AI provider meant widening a function that already mapped a requested model name onto whatever the environment could serve — not introducing a new abstraction.

LessonWidening an existing seam beats inventing one. The four places that call a model all had the same shape, so the change landed in one file.

04

Access denied — four independent gates, one culprit

BrokeThe model was refused for the account, with an error that did not say why.

FixA single command separates the four gates that all have to be open: permissions, account entitlement, regional availability, and the vendor's own terms. Three read fine; only the vendor agreement was missing.

LessonModel access is account governance, not application code. No amount of engineering downstream fixes a missing agreement — and knowing which of four gates is shut is the difference between a five-minute fix and a day.

05

The constraint produced the better design

Being unable to use the preferred model meant dropping that vendor's dedicated client — which only speaks to that vendor — in favour of the provider-neutral interface that handles every model the same way.

LessonSwitching models is now a one-line configuration change rather than a migration, and the originally-preferred model needs no code at all when it is granted. The vendor-specific client would have locked that in.

06

A limit that varies by model, read from the error

BrokeA request exceeded one model's output ceiling — a default that was fine for the model originally targeted and too high for its replacement.

FixRather than maintain a table of per-model limits that goes stale every time a model ships, read the ceiling out of the rejection message, reduce, and retry once. Self-tuning for models that do not exist yet.

Document search for the agents

07

A new account is rate-limited harder than a mature one

BrokeBuilding the index hit throttling at eight concurrent requests, after the default retries were exhausted.

FixSwitch the client to the retry mode that slows itself down based on observed throttling, rather than retrying a fixed number of times and giving up.

LessonThe fallback path earned its keep here: search dropped back to keyword ranking and kept answering instead of failing.

08

Over half the corpus was the same text twice

Removing duplicates cut the corpus by more than half — shared caveats and identical passages repeated verbatim across documents were filling the top results with the same paragraph several times over.

LessonThe best improvement in the whole phase had nothing to do with the technology being evaluated. It improved both ranking methods and halved the ongoing cost. Look at the data before optimising the algorithm.

09

Measured the upgrade — and shipped it switched off

Semantic search lost to keyword matching on this corpus, so it went in behind a setting that defaults to off. See §6.11 for why, and for the honest limits of that measurement.

10

Versioning, not durability, was the reason for object storage

Re-uploading a revised methodology document retained its predecessor. That is what answers "which version was in force when this number was published" — the question a regulator actually asks.

LessonThe storage layout also explained the duplication in entry 08 outright: uploaded copies and original copies were byte-identical. Every document was in the corpus twice, and the file listing said so plainly once it existed.

Blocked — and what that taught

11

Establish the blast radius before deciding what to do

BrokeTwo services refused every call with a subscription error. Not a permissions problem, and not a code problem — no code had been written yet.

FixProbing the whole service surface first made the decision obvious: everything needed for the next phase answered normally, so that phase went ahead untouched and no speculative integration was written for a service that could not be called.

Lesson"This service is blocked" and "the account is blocked" imply completely different plans. Ten minutes of probing separated them.

Getting work off the request path

12

A gate that actually holds

Verified against live infrastructure rather than assumed: work queued and returned immediately, the worker ran it and stored the result, and an execution parked at the approval gate was still parked ten seconds later — then released when its token was answered.

LessonThat parked execution is the entire reason this is a state machine and not a loop in the application. It survives restarts and deploys, and it is inspectable while it waits. A blocked thread in a web server is neither.

BrokePermission changes take time to propagate. The function rejected a role it could not yet see, and creation needed three attempts behind a retry. Better built in than discovered in a pipeline.

13

The same infrastructure, described instead of scripted

A 539-line provisioning script became roughly 130 lines of infrastructure-as-code. Everything cut was bookkeeping: create-versus-update branching, retry loops for permission propagation, wait-for-ready polling, and hand-written policies the tool derives from the wiring.

LessonThe real payoff is the preview. Changing the worker's memory printed exactly what would change before anything was touched. The script had no way to answer "what would this do?" — and that question is the difference between a routine change and a risky one.

Making the drawn canvas actually runnable

14

A correction to an earlier claim on this page

FixAn earlier version of this document said the backend re-interpreted the analyst's canvas. It never did — the canvas was stored as data nothing read. The real gap was two unconnected representations of the same ordering, one in the browser and one in the engine.

LessonKeeping the compiler a pure function paid immediately: the ordering, the cycle check and the name-collision handling were all testable with no credentials at all, and the result could be validated by AWS without creating anything.

15

A version has to mean "what this does changed"

BrokeThe first implementation versioned the whole definition — and the workflow's display name lives inside it. So renaming a workflow minted a new version of a calculation that had not changed.

FixVersion only the executable content. In an audit trail, a version that changes for cosmetic reasons is worse than no version, because it destroys the meaning of the ones that matter.

LessonDeleting infrastructure is asynchronous. A deleted state machine kept appearing in listings for up to a minute, so the cleanup routine reported something it had just removed. Found only by running it twice in quick succession — and on its first run it caught a genuine orphan, which is exactly what it is for.

16

Real models, in an image built by AWS

The evidence decided this rather than a preference: most bundled models load with almost nothing, but two carry heavyweight scientific-computing dependencies. The resulting image is far past the size a plain function allows, so a container it had to be.

BrokeReused containers cross-contaminated. Every model folder ships a companion file under the same name; the language caches the first one imported and the platform reuses that cache, so the first model to load won and every other one failed with a mismatch.

BrokeRaising the worker's time limit broke the deployment, because the queue refuses a configuration where a message becomes visible again before the work could possibly have finished. The code had a comment stating that exact rule — which is precisely why it got broken. It is now derived from the timeout rather than written down beside it.

LessonVerify against a known-good baseline, not merely for the absence of errors. The same model produced identical numbers to six decimal places in the cloud and on a laptop — which is the check that matters when the output is a regulatory figure.

17

A correct result, discarded on the way out

BrokeThe state machine threw away a correct answer because it was told to read a field that only one of the two response shapes contains. The computation succeeded, the workflow failed, and the two facts looked unrelated.

LessonColumn order is load-bearing and silently so. Several of these models take their inputs positionally, so a wrongly-ordered table produces confidently wrong numbers rather than an error. Relying on the order a caller happens to send would have worked by luck.

Moving the state out of the process

18

The only test that mattered

Create a workflow through the API, discard every application module, rebuild the application from scratch, and ask for it again. It is there — with its graph, across an update, and staying deleted after a delete. That is the problem in §2 actually gone rather than argued about.

LessonThe test initially "failed" on its own fallback check, because removing an environment variable does not unset it when the application reloads its configuration file. Setting it empty is what "unset" has to mean there. A test that lies about its own setup is worse than no test.

19

The bug this pattern hides

BrokeA dictionary hands back its own object, so modifying what you fetched was the write. An accessor hands back a copy, so the identical line of code silently persists nothing. Three places depended on the old behaviour, and none of them failed loudly.

LessonMoving storage behind an accessor changes the semantics, not just the mechanism. Fetch-modify-store is the pattern to search for before starting, and it is invisible in a change that otherwise looks like a rename.

LessonThe migration surfaced an unrelated bug that had been there all along: an unknown model id was being reported as a failed calculation rather than as "not found". Rewriting a call site is when you finally read it.

20

A cache that disagreed with the thing it cached

BrokeThe per-request cache first remembered values as handed in. But the database's number handling is not perfectly round-trip faithful, so a read straight after a write disagreed with the same read one request later.

FixRemember what a fresh read would return, not what was passed in.

LessonA cache that is merely fast is easy. A cache that is indistinguishable from the thing it fronts is the one worth shipping — and the test for it is equality against a cold read, not a hit-rate number.

21

Two size limits that are easy to confuse

BrokeA large result exceeded the maximum size of a single record — and the limit counts field names too, so a table of results is mostly repeated column labels. A four-thousand-row test case measured more than twice the limit and was rejected outright.

LessonOne limit applies per record and is enforced when writing; a different one applies per page of results and is enforced when reading. Conflating them leads to fixing the wrong thing.

LessonA test asserting that an operation took more than zero milliseconds failed about one run in three, because this machine's clock only ticks every sixteen milliseconds and fast operations measure exactly zero. The assertion was wrong about the environment, not the code — and an intermittent test is a claim you cannot cite.

22

Ship the code before the infrastructure — but only if it survives the gap

The index-backed listing raises a specific, recognisable error when the index does not exist yet, and the endpoint falls back to the old behaviour. So deploying the code ahead of the infrastructure degrades to yesterday's performance instead of failing. That path was verified against the real database while the index genuinely did not exist.

LessonAlways preview an infrastructure change and read it for replacement, not just content. This table is configured to be deleted along with its stack, so a change the platform treats as a replace would take every record with it. The preview builds a real change set, which is what makes that answerable before committing.

Files, then identity

23

Worse than an obvious failure

Moving the records to a database left the files behind on one machine. That is not a clean break: the record resolves everywhere, so an uploaded dataset appears in every listing, and then reading it fails on every server except the one that received it.

BrokeFetching a model without its companion files fails with an error naming a missing class, not a missing file — a confusing way to discover what is actually wrong. The fetch now brings them along.

LessonThis work exposed a fault that already existed: the startup routine that stages bundled data skips anything already registered. With a shared database, only the first server runs it — and the others were therefore skipping the file copy too. The fix for the new problem covered the old one.

24

A bug only the real thing could show

BrokeTokens minted by the live identity service were rejected as "not yet valid". The service's clock and this machine's clock differ by a fraction of a second, and the check had no tolerance for that.

FixSixty seconds of allowance in both directions — the standard remedy, and now tested from both sides of that boundary.

LessonThe offline test could not have caught this, because it created and verified tokens using the same clock. Only a real deployment has two clocks. Some classes of bug are structurally invisible to a test suite, and knowing which ones is the argument for verifying against the real thing before calling something done.

Finishing the state migration

25

The claim I had already made twice, and had to withdraw

BrokeIdentity was described — here and in the commit history — as the last thing blocking multiple servers. Asked what to build next, I checked instead of recalling, and found six more registries holding analyst-created work in memory: charts, Python tools, dashboard layouts, playbooks, analytic definitions, warehouse connections.

LessonOne search for module-level dictionaries answered in a minute what I had twice asserted from memory. "Where does state live?" is an enumeration question. Anything less is a guess wearing a confident sentence.

LessonThe failure modes differ in a way worth naming. Auth would have broken every request — roughly half of them with two servers. These six break a feature: you build a chart, refresh, land on the other server, and it is gone. Less total, and considerably more confusing to diagnose.

26

Protecting the database before putting more into it

Point-in-time recovery on, and the records database retained independently of the stack that creates it. Confirmed by querying the live database, not by reading the deployment output.

LessonThis had been flagged three times and deferred three times, while everything built on top of that database assumed it mattered. The configuration said otherwise. The gap between what a system assumes and what it is configured for is where this kind of loss actually happens — and it was two lines.

27

The same bug, nine more times

Four registries moved — charts, layouts, connections, tools — and the difficulty was where it was last time: nine places that read a record, changed a field, and used to be finished, because the object they held was the registry's.

FixOne of them was a helper that handed callers the registry itself so they could mutate through it. It now returns a save function instead, which makes the write impossible to forget rather than merely documented.

BrokeA test written for the mutation sites I had planned for caught one I had not: testing a warehouse connection set its status and timestamp and persisted neither. Writing the test for the general pattern, rather than for the specific sites, is what found it.

LessonA registry that already persisted to a local file looked done and was not. Durable and shared are different properties, and a file on one machine's disk has only the first.

28

Two dicts, two different answers

Analytic definitions are a handful of authored records and took the plain treatment. Their runs are append-only, unbounded, and each carries a full result table — so they took what the other run history took: a size guard and a time-ordered index.

LessonChecking the schema rather than assuming symmetry is what decided that. Two registries in the same file needed opposite answers, and the difference was visible only in what their records contain.

LessonWhere the note about a dropped payload goes matters. It went in the human-readable narrative field, not the error field — a completed run annotated in error reads as a failed one, and a record that misleads is worse than a record that is merely incomplete.

29

Verifying the thing that had never been verified

The new record types had only been exercised against the in-memory fallback. Two things were genuinely untested against the real database: how these particular records serialise, and a second kind of record writing into the shared index — until now only run history used it.

Lesson"Two partitions in one index do not collide" is obviously true right up until it is not. It cost one throwaway test to stop assuming, and the same test confirmed the existing partition was untouched.

LessonThree times in this stretch a test was wrong about the schema while the code was right. That is the healthier direction for errors to run, but it is also a signal: a test written from memory of an interface tests the memory, not the interface.

Closing the last three gaps

30

The one thing infrastructure-as-code refuses to do

Moving the AI provider's key out of the configuration file looked like a one-line addition to the stack definition: declare an encrypted parameter, done.

BrokeThe template format has no encrypted-value type. It accepts plain strings and lists of strings, and nothing else — so there is no way to declare the thing at all, let alone declare it safely.

FixA short script writes the parameter once, and the application reads it at startup before the modules that need it are imported. The script deliberately does not then edit the configuration file for you: deleting the only copy of a key before anyone has confirmed the remote one reads back is a bad afternoon, so it prints the line to remove instead.

LessonThis is a refusal, not a gap someone will close. A template is a plaintext document that ends up in a console, in change sets, and in every diff. The deeper rule underneath it: a secret whose value you did not generate cannot originate in infrastructure code — something has to carry it in from outside, once, and the honest design is the one that says so rather than hiding the step.

31

Owned, referenced, and the difference between them

The other half of the retention work was object lifecycle rules, which the plan had described as "a few lines" in the stack definition.

BrokeIt was not. The bucket predates the stack, so the definition references it by name rather than creating it — and a reference can be granted access, but cannot have properties set on it. The plan's own estimate was wrong, and writing the code was how that surfaced.

FixA second script, opening with the reason it is not part of the stack. It prints the bucket's existing configuration before replacing it, because the underlying call overwrites the whole configuration rather than merging into it — a detail that turns "add one rule" into "silently delete the others" for anyone who assumes otherwise.

LessonAn estimate written while reading a document is not the same as one written while reading the code. This one had been sitting in the plan for weeks, stated with confidence, and cost nothing to correct only because it was caught before the work was scheduled rather than after.

LessonA related trap in the same rules: on a versioned bucket, expiring an object only writes a deletion marker — the bytes stay, and stay billed, until a second rule expires the superseded versions. It is the most common way a lifecycle rule appears to work and does nothing.

32

The dormant bug that only mattered once the data moved

Moving uploaded skills into object storage is the same write-through pattern the datasets already used, so it should have been the easy half of the last migration step. The test that proved it worked failed on the first run — but not where it was pointed.

BrokeSaving a skill and deleting one had disagreed about the filename for as long as both had existed. The writer kept hyphens; every lookup converted them to underscores. Since skills are named in kebab-case by convention, the two never matched for any real skill, and deleting one reported it missing.

LessonIt had been harmless. A file nobody could delete through the interface was a nuisance on a single server, and the folder was empty in practice, so nothing surfaced it. Making the shared copy authoritative changed that completely: a delete that cannot find its file also cannot remove the shared one, and the next reconcile would faithfully restore what the user had just deleted. A latent bug is not a small bug — it is a bug whose blast radius is determined by what you build on top of it. The migration did not introduce this one; it promoted it.

FixOne naming function, used by every writer and every lookup, plus a fallback so files written under the old convention are still removable rather than stranded. The narrow fix — teach the delete path the other spelling — would have left two conventions in a codebase that now uses the filename as a storage key.

LessonThe first startup after the change published two search-index files that had been sitting on one machine for months. Uploading only at the moment of a rebuild sounds sufficient and is not: a rebuild happens when the corpus changes, so files built before the seam existed would have stayed where they were indefinitely. Reconciling in both directions at startup is what actually moved them.

Giving the application somewhere to run

33

A convenience wrapper that only failed once it was useful

Deployment had become four commands in a fixed order, so they were wrapped in one. It ran clean twice, then broke on the first deploy that actually changed something — in two unrelated ways, both of which had been there since it was written.

BrokeIt read the deployment tool's output using the operating system's regional text encoding, while the tool emits box-drawing characters and symbols in its diff. Any diff with real content in it crashed the wrapper. The earlier runs had survived only because "there were no differences" contains nothing but plain letters.

LessonThe failure appeared at the exact moment the tool first did something, which made it look like the change under review had caused it. A convenience layer that is only exercised on the no-op path has not been tested; it has been visited.

BrokeWorse, and a design mistake rather than a slip. The wrapper asked the deployment tool to prompt for confirmation on permission changes. Without an interactive terminal the tool cannot prompt, so it refuses outright — meaning every deploy touching permissions failed from automation, from a script, and from the way the wrapper was actually being used. It reported nothing obviously wrong; the infrastructure simply stayed as it was.

FixTurn the prompt off, which needs justifying because it reads like disabling a safety check. It is not — the check moved. The wrapper already prints the permission-change table as part of the review step, and then requires a second, separate command before anything is applied. The person running it has already seen precisely what the prompt would have shown. Asking the same question twice inside one command is how people learn to answer it without reading.

LessonBoth bugs share a shape worth naming: a safeguard you have never seen fire is a safeguard you have never tested. The same deploy was the first time the wrapper's own replacement guard fired — it flagged a budget change as possibly destructive, which was right to surface and turned out to be conservative, since the platform updated the budget in place. That is the correct direction for that kind of check to be wrong in, and the only reason anyone knows it works is that it finally had something to say.

34

The build that worked first time, and why that is worth recording too

The web-tier image had never been built. The expected failures were dependency resolution against a newer Python, and imports from the domain packs that the file list had missed.

LessonNeither happened: 102 seconds, 259 MB, first attempt. Recorded because a log that only contains disasters quietly teaches that everything is hard, and the reason this one was not is visible in the preceding entries — the image copies an explicit list of directories rather than the whole tree, so there was no ambiguity about what belonged in it, and the dependency list was pinned to the same floors the application already declared. The build was boring because the decisions before it were not.

LessonA successful build still proves only that the image assembles. It says nothing about whether the application starts inside it, which is a different question answered by a different failure, at a cost of roughly thirty-four dollars a month to ask.

35

The line in the log that the whole migration was for

The first deploy of the web tier brought up two servers behind a load balancer, both healthy, answering in about two hundred milliseconds. Nothing failed, which was not the expectation — a container image that has never been run usually fails its first health check.

LessonThe interesting output was not the successful request. It was one line, printed identically by both servers as they started: pulled 2 prebuilt index files, published 0. Neither had ever embedded anything, and neither needed to, because the other had already paid that cost and left the result where both could find it.

That line is the whole argument in miniature. Without it each server would have quietly fallen back to keyword search while it rebuilt, and for those minutes the same question would have returned different answers depending on which server the load balancer picked — no error, no alarm, nothing to grep for. Every earlier entry in this log was in service of that line being boring.

LessonWorth being precise about what was and was not proved. Two replicas ran, shared their stores, and agreed. Nobody has yet logged in and driven an analysis end to end through the deployed system, which needs a credential this work did not have. "It starts and is healthy" and "it is correct" are separated by exactly the kind of gap this document keeps finding.

Three problems that turned out to be one purchase

The remaining list read: the browser application has nowhere to be served from, the interface is unencrypted, and cross-origin permissions are configured for a developer's laptop. Three entries, three efforts, in three different places.

LessonThey were one thing. A content delivery network in front of the existing load balancer supplies a certificate — which the load balancer cannot have on its own, because certificates are issued against domains and nobody owns the one it was given. It also serves the compiled application, and puts the application and the interface on a single address, which does not so much configure cross-origin permissions as delete the question. At this volume the network is free. The reason to look for the shape is not elegance; it is that three separate efforts would each have been individually justified and collectively wasteful.

BrokeNearly. The application uses real paths for its internal navigation, so a bookmarked page has to be answerable directly. The obvious lever is the network's "when something is missing, serve the main page instead" setting — and it applies to everything, so it would have turned genuine "no such record" answers from the interface into a web page reporting success. A working application in front of an interface that lies.

FixA tiny function attached to the application's traffic only, rewriting anything that looks like a route rather than a file. The interface's traffic never sees it. The general lesson: a setting that reads as a per-section option and is documented as a whole-system one is worth checking before relying on it — the failure it would have caused is silent and would have been blamed on the application.

LessonOne deliberate non-change is worth recording. Nothing in the browser application was modified. It had always requested data using relative addresses, which meant it needed no notion of where the interface lived — and that decision, made long before any of this, is the reason a change of address cost nothing.
